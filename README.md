# UX 시나리오 설계 Agent

**팀 독립선언문 · LG전자–국립창원대 AX 해커톤 Theme B (UX/UI 시나리오 설계자)**

고객 상황을 입력하면 **UX 시나리오를 생성하고, 그것을 실제로 실행해 검증한다.**
지시를 받아 가전을 돌리는 것이 아니라, 시나리오 설계라는 **직무를 반복 수행한다.**

```
입력: 고객 상황          출력: UX 시나리오 + 실행 결과
Goal → Plan → Tool·Skill → Execute → Evaluate → Output
```

## 실행

```bash
python run_design.py            # 고객 상황 4건 → 시나리오 4건 (주 산출물)
python run_design.py p1_야근    # 한 상황만
python run_demo.py              # 실행 층만 단독 — 스킬 재사용 실증
python run_repeat.py            # 같은 상황 두 번 — 기록이 다음 목표가 되는지
python run_share.py             # 본가 기록을 자취방·원룸 기기로 이식
python stress_test.py           # 일부러 망가뜨린 입력 19건
python thinq.py "오늘 늦어. 9시 반 도착이고 배추랑 두부 있어"   # 자연어로 받기

python check_all.py             # ← 전부 돌린다. 실패하면 무엇부터 볼지 알려준다
python check_all.py --fast      #   분산 측정(200회)을 건너뛴다

python check_regression.py      # scenarios.json 회귀 검사
python check_consistency.py     # 선언·물리·문서·맞물림·주장 11항목 검사
python check_interlock.py       # 스킬 절단 실험 — 각 단계가 뒤에 실제로 영향을 주는가
python check_generalize.py      # 설계하지 않은 상황 5종에서도 이유를 남기고 끝나는가
python check_skills.py          # 스킬 11종 단독 — 순수성·경계값·근거·정직성·격리·계약
python check_reuse.py           # reusable_for 가 말뿐인지 — 주방 밖 8개 대상에 실제 적용
python check_planner.py         # 순서를 정말 계산하는가 — 결정성·최소성·순환·한계
python check_physics.py         # 무작위 조작 불변량 + 에너지 수지·끓는점·규모·뚜껑 정량 검산
python check_cooking.py         # 조리 상식이 코드에서 성립하는가 (14항목)
python check_sensitivity.py     # 어느 상수가 결과를 지배하는가 (가정값 감시)
```

API 키가 없어도 전부 동작한다. 계획은 LLM이 아니라 **전제조건 플래너**가 계산한다.

## 핵심 결과

상황이 다르면 **계획 자체가 달라진다.** 순서는 코드 어디에도 적혀 있지 않다.

조리량·가열 시간·세척 코스가 상황마다 다른 것은 **가구원 수와 그 집 냄비**가
다르기 때문이다.

| 상황 | 조리량 | 가열 | 세척 | 기대 물 | 기본 대비 | 손이 가는 일 |
|---|---|---|---|---|---|---|
| 야근 1인 | 2인분 기록 → 1인분 | 5.5분 | 에코 | 8.3L | **−3.5L** | 3회 / 조리 5.5분 |
| 맞벌이 2인 | 그대로 2인분 | 7.75분 | 표준 | 11.8L | 0L | 3회 / 7.75분 |
| 알레르기 4인 | 공개 1인분 → 4배 | 20.85분 | 강력 | 16.8L | **−1.4L** | 5회 / 20.85분 |
| 퇴근길 1인 | 2인분 기록 → 1인분 | 5.5분 | 에코 | 8.3L | **−3.5L** | 3회 / 5.5분 |

물 절감은 **기본 코스가 틀렸을 때만** 생긴다. 4상황 평균 2.1L 이며,
요리와 양이 달라지면 이 값도 달라진다.

| 고객 상황 | 계산된 가전 작업 순서 | 선택 메뉴 | 개입 | 장면 |
|---|---|---|---|---|
| 야근 1인 가구 | inventory → recipe_source → menu → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 4/4 |
| 맞벌이 2인 가구 | … → **procure** → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 4/4 |
| 알레르기 4인 가구 | … → **procure** → prep → converge → aftercare | 호박잎 삼계탕 (**공개 레시피**) | 2회 | 5/5 |
| 퇴근길 1인 가구 | … → **procure**(선제) → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 4/4 |

1인 가구는 귀가 후 25분뿐이라 조달(20분 예상)이 예산을 넘는다.
Agent가 `stock_complete`를 이미 성립한 사실로 두자 플래너가 **`procure`를 스스로 제외**했다.
알레르기 가구는 공개 레시피를 알레르기 25건·나트륨 27건 걸러 48건을 남기고, 그중
**끓이기**이면서 **오늘 안에 재료가 오는** 것 가운데 내일이면 버려야 할 닭고기(1일 남음)를
쓰는 호박잎 삼계탕을 골랐다. 찹쌀·미나리는 처음 사는 품목이라 자동 주문하지 않고
물었고(개입 2회 = 설계된 정지), 승인하면 즉시배송을 **20분 기다린 뒤** 끓인다 — 식사까지 49.9분.

> **2026-09-28 에 고친 것.** 전에도 삼계탕을 골랐지만, 찹쌀을 "제때 오는 상점이 없다
> (720분)" 고 물어 놓고 승인을 가정해 **그 자리에서 재고에 넣었다.** 없는 찹쌀로 끓이고
> 그 찹쌀이 빨아들일 물 1090g 까지 부었으며, 식사까지 29.9분으로 쟀다. 고친 뒤에는
> (1) 메뉴가 오늘 안에 못 오는 재료가 필요한 후보를 빼고, (2) 승인해 산 것도 배송을
> 기다리며, (3) 이 조리기가 하는 **끓이기**만 후보로 둔다(샐러드·주스·튀김을 냄비에서
> 졸이던 것을 뺐다). 상점 목록은 공개 레시피 재료에서 골라 넓혔고, 즉시배송이 찹쌀을
> 파는지가 결과를 가른다 — 빼면 삼계탕 대신 된장찌개가 되고 닭고기는 "오늘 쓰는 메뉴가
> 없다" 로 알린다.
퇴근길 가구는 **퇴근 시각을 알기 때문에** 이동 40분 안에 배송이 끝난다 —
냉장고와 양념 선반을 함께 확인해 두부·참기름을 귀가 시각에 맞춰 주문하고, 개입은 0회다.

## 두 번째 조리는 달라진다

```bash
python run_repeat.py            # 기본 p3_알레르기
```

| | 쓴 기록 | 목표 질량비 | 출처 | 가열 | 먹기 직전 |
|---|---|---|---|---|---|
| 1회차 | `pub_639` | 0.85 | 조리법 기본값(가정) | 20.85분 | 0.8494 |
| 2회차 | **`rec_004`** | **0.8494** | **실측 기록** | 21.05분 | 0.8494 |

목표가 **가정값 0.85 에서 내 주방의 실측 0.8494 로** 바뀌었다. 차이는 작지만
출처가 바뀐 것이 핵심이다 — 같은 메뉴를 두 번째 만들 때부터는 남의 평균이
아니라 내 주방에서 실제로 나온 값을 쫓는다(목표는 새 정보가 있을 때만 갱신한다).

조리가 끝나면 이번 실측이 기록으로 저장되고, 다음 번 목표가 된다.
공개 레시피의 가정값을 **내 주방에서 나온 값**이 대신한다.

| | 초기 질량 | 목표 | 도달 시간 | 먹기 직전 |
|---|---|---|---|---|
| 본가 6인용 | 618g | 0.78 | **7.7분** | 0.7799 |
| 자취방 2인용 | 206g | 0.78 | **3.4분** | 0.7800 |
| 원룸 1인용 | 103g | 0.78 | **2.35분** | 0.7800 |

가져간 것은 **목표 질량비**(비율이라 용량 무관), 줄인 것은 재료량, 버린 것은 **조리 시간**이다.
시간을 복사했다면 작은 냄비는 7.7분에 크게 지나쳤을 것이다.

**용량 비율은 코드 어디에도 적혀 있지 않다.** 기기가 자기 제원(인분·용량)을 알고 있고,
`record_import` 가 두 기기의 제원에서 비율을 계산한다 — 냄비가 바뀌면 기기 이름만 달라진다.
등록되지 않은 기기는 추측하지 않고 비율 1 로 두면서 "제원을 모른다" 고 말한다.

## 요리로서 챙긴 것

질량비 하나만 쫓으면 그건 "액체 졸이기" 지 요리가 아니다. 제안서가 적어 둔
것 중 코드에 없던 것과, 요리라면 당연한 것을 넣었다.

| 무엇 | 왜 | 결과 |
|---|---|---|
| **조리 단계(중간 투입)** | 두부를 처음부터 넣으면 부서진다. 제안서는 "재료 투입 전후를 구분한다" 고 적었는데 코드엔 없었다 | 질량비 0.93 에서 투입, 온도 **30도 하강** 후 재가열. 기준을 다시 잡아 진행률·ETA 가 무너지지 않는다 |
| **여열** | 숙련자는 목표에 닿고 나서 끄지 않는다. 미리 끈다 | 기기가 자기 여열을 예측(오차 0.37g)하고, 제어기가 그만큼 앞당겨 끈다. 모자라면 **다시 켜고** 예측 신뢰도를 낮춘다 |
| **몇 인분인가** | 4인 가구가 1인분(237g)을 조리하고 있었다. 가구원 수는 '세척까지 할지' 에만 쓰였다 | 기록의 인분 수와 가구원 수로 조리량을 정하고, **기기 용량이 상한**이 된다 |
| **끓어넘침 감지** | 제안서는 "가열 상한, 이상 감지" 를 약속했는데 상한(화력 5)만 있었다. 상한은 사양이지 상황 판단이 아니다 | 채움 비율 × 끓음 × 화력으로 위험을 재고 화력을 묶는다. 위험이 지나가면 **되돌린다** |

### 요리 중에 실제로 일어나는 일들

| 무엇 | 왜 중요한가 | 확인한 값 |
|---|---|---|
| **물을 먹는 재료** | 찹쌀 400g 은 국물을 800g 먹는다. 총 질량은 그대로라 **질량비만 보면 아무 일도 없어 보인다** | 물을 안 채우면 0.9336 에서 국물이 바닥나고 눌어붙음 1.0 |
| **물은 얼마나** | 흡수량만 채우면 졸일 물이 없다. `M ≥ (고형+흡수)/목표비율` | 삼계탕에 1090g 을 더 붓는다 (찹쌀이 실제로 도착한 뒤) |
| **뚜껑** | 덮으면 증기가 갇혀 더 높은 온도까지 오르고, 열면 증발이 급등한다 | 6분 뒤 **열면 78.5도 / 덮으면 97.0도** |
| **거품 걷기** | 질량이 주는데 **증발이 아니다.** 분모에서 빼지 않으면 졸은 것으로 샌다 | 1000g → 955g, 비율은 1.0 그대로 |
| **젓기** | 안 저으면 바닥이 눌어붙는다. 교반은 사람이 하는 일(제안서 표1)이라 **안내**한다 | 눌어붙음 0.092 → **0.0506** |
| **물로 되돌리기** | 졸이는 것은 되돌릴 수 없다고 가정했지만, 물을 부으면 된다 — 다만 묽어진다 | 오차 0.0242 → **0.0000**, 국물 3.1% 묽어짐 |

되돌리기는 **여열이 끝난 뒤**에 해야 한다. 불 끈 시점에 맞춰 부으면 남은 열로
다시 졸아든다. 그리고 묽어짐이 6% 를 넘으면 되돌리지 않고 지나친 채로 알린다.

### 누가 요리하는가 — 로봇이 아니다

제안서 표1 은 **"재료 손질·계량·투입, 필요 시 교반"을 사람 몫**으로,
"가열 제어 또는 조절 안내"를 시스템 몫으로 적었다. 그런데 코드는 투입·뚜껑·
거품까지 스스로 하면서 **"개입 0회"라고 보고**하고 있었다. 로봇이 아닌데
로봇처럼 굴었다.

가전이 실제로 할 수 있는 것은 **화력 조절과 판단·기록**뿐이다. 나머지는
사람의 손이 필요하고, 에이전트의 값은 그것을 **대신 하는 것이 아니라
언제 해야 하는지 정확히 알려주는 것**이다.

| 상황 | 손이 가는 일 | 냄비 앞에 있어야 하는 시간 |
|---|---|---|
| 야근 1인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 5.5분 |
| 맞벌이 2인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 7.75분 |
| 알레르기 4인 | 5회 (뚜껑 2, 거품 1, 교반 2) | **5분** / 조리 20.85분 |
| 퇴근길 1인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 5.5분 |

에이전트가 없으면 **언제 해야 할지 모르므로 조리 내내 지켜봐야 한다.**
그러니 값은 "개입 0회"가 아니라 **"지켜보는 시간이 20.85분에서 5분으로"** 다.
상황에 따라 조리 시간의 **24~55%** 이며, 양이 많고 오래 끓일수록 비율이 낮다
(4인분 24% / 1인분 55%) — 손이 가는 횟수는 비슷한데 조리가 길기 때문이다.
`user_touches`(되돌릴 수 없는 결정에 대한 확인 요청)와 `hands_on`(손이 가는
일)은 다른 지표이며, 둘을 나눠 보고한다.

### 열 모델 — 1차 지연에서 열량 수지로

예전에는 온도를 `T += (목표온도 - T) * k` 로 밀었다. 그러면 두 가지가 틀린다.

- 양이 달라도 데우는 시간이 같다 (310g 과 2000g 이 둘 다 3.75분)
- 출발 온도 차이가 지수적으로 사라진다 (냉장 재료를 넣으나 마나)

실제 화구는 **일정한 열량**을 넣는다. 온도는 열량 수지로 정해지고, 끓는점에
닿으면 남는 열은 온도가 아니라 **증발**로 간다.

| | 고친 뒤 |
|---|---|
| 310g / 620g / 2000g 끓기까지 | **2.0 / 3.25 / 8.25분** (양에 비례) |
| 20도 출발 vs 6도 출발 | **3.25분 vs 3.75분** (차이가 유지된다) |
| 화력 3 끓는 중 증발 | 20.9 g/분 |
| 여열 예측 오차 | **0.01g** (예측 3.29 / 실제 3.30) |

여열 구간은 **"불 끄고 상에 올리기까지 3분"** 으로 정의했다. 열량 수지로
바꾸자 끓음이 멎은 뒤에도 표면 증발이 계속돼 **끝나는 지점이 사라졌기**
때문이다(15분 두면 11.3g). 여열은 물리 현상이지만 "얼마나 두는가" 는
사람의 행동이라 명시해야 한다.

그리고 `converge` 는 **불을 끄는 시점까지만** 담당한다. 끈 뒤의 여열까지
붙들고 있으면 호출자가 다시 여열을 돌릴 때 **두 번 적용**된다 —
실제로 그래서 여열을 쓰는 쪽 오차가 더 컸다(0.0084 → 고친 뒤 0.0031).

상수는 두 가지 실제 값에서 역산했다 — 620g 을 불 끄면 100→90도가 약 3분
(방열 2.28 W/K), 화력 3 으로 20→100도가 약 5.5분(화력당 298 W).
둘 다 가정이며 실측으로 교체해야 하는 자리다.

### 시간이 맞는가 — 제안의 핵심 주장인데 검증하는 곳이 없었다

"귀가 후 25분 안에 제대로 된 한 끼" 가 제안의 주장인데, 검증은 장면 달성과
개입 횟수만 보고 있었다. 그리고 **주문한 재료가 도착하기 전에 조리를
시작하고 있었다** — "20분 뒤 도착" 이라 해놓고 주문 즉시 재고에 넣었다.

| 상황 | 조달 | 식사까지 | 예산 |
|---|---|---|---|
| 야근 1인 | 없음 | 14.6분 | 25분 |
| 맞벌이 2인 | 주문 후 **20분 대기** | 36.9분 | 45분 |
| 알레르기 4인 | 확인 요청 2건 | 30.2분 | 60분 |
| 퇴근길 1인 | **이동 중 도착** | 14.5분 | 25분 |

맞벌이와 퇴근길은 같은 메뉴인데 **22.4분 차이**가 난다. 그 전부가 배송을
기다리는 시간이고, 퇴근 시각을 알면 그 시간이 이동에 묻힌다.
이것이 선제 주문의 값이다 — 이제 숫자로 나온다.

### 익힘과 졸임은 다른 조건이다

제안서는 "익힘·졸임의 판단이 어려운" 사용자를 대상으로 적었는데 코드에는
졸임만 있었다. 질량비가 목표에 닿아도 닭고기가 안 익었으면 끝이 아니다.

`converge` 는 완료 조건을 둘 이상 가질 수 있다. 졸임이 먼저 끝나면
**화력을 유지하며 익을 때까지 기다리고**, 그 사이 더 졸면 물로 되돌린다.
유지 화력을 1 로 두었더니 53도로 식어 익지 않았다 — 3 이어야 한다.

### 요리 물리에서 찾은 모순

기능이 도는 것과 물리가 맞는 것은 다르다. 값을 하나씩 찔러 보고 찾았다.

| 무엇 | 증거 | 고친 것 |
|---|---|---|
| **찬물을 부어도 온도가 그대로** | 50g 부었는데 100.0 → 100.0도 | 재료 투입과 같은 질량가중 평균 (8.5도 하강) |
| **냄비를 넘겨도 말이 없다** | 1000g 냄비에 1200g(120%) | 투입 시 채움 비율을 보고 경고 |
| **늦게 넣은 재료가 이미 익어 있다** | 8분에 넣은 고기가 0분부터 익은 것으로 | 요구량을 늘려 덜 익은 것으로 본다 |
| **뚜껑이 넘침과 무관** | 덮으나 여나 위험 0.78 | 거품이 갇히므로 1.6배 (0.78 → 1.0) |
| **거품을 걷으면 국물이 준다** | 걷은 50g 이 전부 국물에서 빠짐 | 거품은 단백질·기름이다 — 고형분에서 80% |

### 여열 보정은 언제 이득인가 — 재보고 정했다

"미리 끄면 더 정확하다" 는 그럴듯하지만 항상 참이 아니다. 120시드로 쟀다.

| 관측 주기 하한 | 여열 보정 끔 | 여열 보정 켬 |
|---|---|---|
| 0.1분 | **0.0030** | 0.0052 |
| 0.5분 | 0.0062 | **0.0052** |
| 1.0분 | 0.0135 | **0.0049** |

관측을 자주 할 수 있으면 목표 바로 앞까지 잘게 다가가면 되고, 그때 여열을
미리 빼는 것은 **예측 오차를 들여오는 일**이다. 관측이 드물면 반대다.
그래서 `converge` 는 **한 걸음의 크기와 여열 크기를 비교해 스스로 정한다.**

## 검사가 깨지면 무엇을 하는가

검사를 만들어 두는 것과 **깨졌을 때 옳게 대처하는 것**은 다른 문제다.
가장 쉬운 길은 늘 기대값을 고쳐 통과시키는 것이고, 그러면 검사는
통과하지만 아무것도 지키지 않는다.

하루 동안 실패 네 건에 서로 다른 대처를 했다. 그 기록을 남겨 둔다.

| 실패한 것 | 원인 | 한 일 |
|---|---|---|
| `check_physics` 질량 수지 41건 | **검사 식이 틀림** (skim 이 분모도 줄이는 것을 몰랐다) | 검사를 고침 |
| `check_cooking` 익힘·표류 | **시험 설계가 틀림** (포화 상태에서 잼 / 방어를 우회함) | 시험을 다시 짬 |
| `check_consistency` 문서 수치 | 코드를 고쳐 값이 바뀜 | 문서를 갱신 |
| `check_sensitivity` STIR_RELIEF | 가정값이 실제로 결과를 지배 | **기준을 완화**하고 한계로 등록 |

**넷 중 둘은 코드가 아니라 내 검사가 틀린 것이었다.** 그래서 순서를 정한다.

```
1. 내 검사·시험이 틀렸는가      ← 가장 먼저 (실제로 하루에 세 번)
2. 산출물이 낡았는가            ← run_design.py 부터 다시
3. 코드가 틀렸는가              ← 고친다
4. 기준이 낡았는가              ← 그 기준을 정한 설정이 바뀌었는지 확인 후에만
5. 한계로 등록                  ← 위 넷이 아닐 때만, 무엇이 뒤집히는지 수치로 적는다
```

`check_all.py` 가 실패한 검사마다 이 순서를 출력한다. 기준을 바꿨으면
**왜 바꿔도 되는지 주석에 남긴다 — 남길 수 없으면 아직 원인을 모르는 것이다.**

## 어느 상수가 결과를 지배하는가 — 민감도

상수마다 출처를 적어 두었다(측정에서 역산 / 실제 조리 관찰 / 시뮬레이터
가정). **결과를 지배하는 것이 가정값이면 그 수치를 근거로 쓸 수 없다.**
그래서 상수를 20% 씩 흔들어 출하 지표가 얼마나 움직이는지 잰다
(`check_sensitivity.py`). 각 상수는 **그것이 실제로 쓰이는 시나리오**에서만
잰다 — 뚜껑을 안 덮는 판에서 뚜껑 상수를 흔들면 당연히 0 이 나온다.

| 상수 | 출처 | 출하 지표를 움직인 폭 (허용 폭 대비) |
|---|---|---|
| `STIR_RELIEF` | **가정** | **66.2%** (눌어붙음 0.5404 → 0.6066) |
| `WATT_PER_POWER` | 역산 | 48.5% |
| `LATENT_J_PER_G` | 역산 | 48.0% |
| `ABSORB_RATE` | 가정 | 10.4% |
| `LOSS_W_PER_K` | 역산 | 9.3% |
| 나머지 가정값 | 가정 | 2.8% 이하 |

### 자연어로 받는다 — LLM 을 어디에 두고 어디에 두지 않는가

LG 가 IFA 2026 에서 공개한 **씽큐 클로**는 카톡·텔레그램으로 대화하고,
루틴에 맞춰 가전 동작을 먼저 제안하며, **실행은 사람이 승인**한다.
하는 일을 뜯어보면 `자연어 → 제안 → 승인 → 실행` 이다.

우리 파이프라인은 `상황 → 계획 → 실행 → 지표` 다. 가운데는 이미 있고
**양 끝이 비어 있었다.** `thinq.py` 가 그 두 끝이다.

```
[LLM 제안]  자연어 → 상황 dict                 → 형식·범위 검사, 안전 항목은 사람 승인
[LLM 제안]  수고 → 시나리오 장면 (llm_design)   → 없는 기능·수치 약속을 버림, 실행으로 판정
[결정적]    계획 → converge → aftercare         ← 손대지 않는다
[LLM]       지표 → 사람이 읽는 문장             → 지어낸 수를 표시
```

원칙은 **"LLM 이 제안하고, 되돌릴 수 없는 결정은 검증된 계산이나
사람이 확정한다"** 다.

처음에는 "판단은 측정이 하고 LLM 은 말만 한다" 로 적었는데 너무 넓었다.
**제어**(화력·불 끄는 시점)에 LLM 을 넣지 않는 것은 맞다 — 관측 주기가
0.25~1분인데 호출이 30~60초 걸리고, 졸아 버린 국물은 되돌릴 수 없고,
200회 반복 측정과 회귀 검사가 "같은 입력이면 같은 출력" 위에 서 있다.
하지만 **사람 말을 이해하는 판단**(이 불편을 어느 기능이 덜어 주는가)은
규칙이 약하고 LLM 이 강하다. 그것까지 막을 이유는 없었다.

### LLM 이 시나리오 장면을 제안한다 (llm_design.py)

장면 틀(kitchen_beats)은 수고를 "덮었는지" 를 **문자열 포함**으로 센다.
그래서 사람이 자기 말로 한 불편은 하나도 못 덮었다.

| 입력 | 틀 | LLM 제안 (진짜 호출) |
|---|---|---|
| "냄비 앞에서 기다리는 것", "퇴근하고 뭐 해먹을지 고민하는 것" | **0/2** | 2/2 |
| p3(알레르기) 페르소나 | 장면 5/5 인데 **수고 1/4** | 수고 3/4 · 장면 6/6 |

p3 의 "재료마다 알레르기 여부를 확인하는 일" 은 menu 의 기피 필터가
실제로 덜어 주는데, 글자가 틀과 달라 세지 않았다. 남은 하나("조리 기구가
섞이지 않게 신경 쓰는 일") 는 LLM 이 **덜어 줄 기능이 없다고 스스로
밝혔다** — 재료만 거르고 도마·칼은 보지 않는다는 이유였고, 맞다.

LLM 이 정하는 것과 코드가 정하는 것:

| | 누가 |
|---|---|
| 불편마다 어느 기능이 덜어 주는가, 장면 문장 | LLM |
| 고를 수 있는 기능 목록 | **flow_design 을 실제로 돌려** 이번 계획에 든 것만 |
| 장면이 일어났는지 볼 지표 이름 | 도메인(KITCHEN_CAPS) |
| 없는 기능을 약속한 장면 ("로봇팔이 썬다", p1 의 "주문한다") | 버림 |
| 실행 전에 수치를 약속한 장면 ("12분 만에") | 버림 |
| LLM 이 빠뜨린 수고 중 틀이 덮는 것 (알레르기 장면) | 틀 장면으로 채움 |
| 선제 주문이 아닌데 귀가 전에 놓은 장면 | 귀가 시각으로 옮기고 기록 |
| 장면이 실제로 일어났는가 | experience_verify 가 실행해서 |

마지막 줄이 실제로 걸렀다. 자유 문장에서 LLM 이 "뭐 해먹을지 고민" 을
재고 기능에 이었는데, 그 사람 냉장고에는 급한 재료가 없어 **"임박한
재료를 먼저 고른다" 는 장면이 미달성으로 판정됐다.** 제안이 실행으로
걸러지는 구조가 동작한 사례다.

LLM 답은 매번 다를 수 있으므로 **받은 원문을 남긴다.** p3 에 준 원문을
`fixtures/` 에 저장해 두고 `check_thinq` 가 키 없이 재생한다 — 두 번
돌려도 같은 시나리오가 나온다.

### 알레르기 — 읽는 쪽이 옳아도 받는 쪽이 모르면 샌다

LLM 이 "갑각류를 못 드셔" 에서 `갑각류` 를 정확히 읽었는데, 레시피 판정이
문자열 일치라 **공개 자료 100건 중 갑각류가 든 15건이 하나도 안 걸렀다.**
규칙 파서는 "못 드셔" 를 아예 못 읽었다. 검사는 "새우 알레르기" 같은
구체어만 넣어서 통과하고 있었다.

* 범주어를 구체 재료로 푼다 (`recipe_parse.CATEGORY`) → 15건 → **0건**.
  풀자 "얇게 썬" 의 `얇게` 가 게로 걸려 부사들을 뺐다.
* 알레르기를 읽으면 **승인 없이는 실행하지 않는다**(기본값이 멈춤).
  전에는 "확인 필요" 를 적기만 하고 그대로 실행했다.
* 표에 없는 범주어(`곡류`)는 승인이 있어도 멈춘다 — 아무것도 안
  걸러지는데 사용자는 걸러졌다고 믿기 때문이다.

검사가 그것을 지킨다 — 같은 상황을 규칙으로 읽든 LLM 으로 읽든
**제어 결과**(가전 순서·개입·가열·질량비)가 같아야 한다(`check_thinq`).

### 받은 값을 그대로 믿지 않는다

LLM 은 그럴듯한 값을 지어낸다. 읽은 값은 형식·범위를 검사하고, 틀리면
기본값으로 돌아간다.

| LLM 이 준 값 | 어떻게 되는가 |
|---|---|
| `time_budget_min: 9999` | 범위 밖 → 버림 |
| `household_size: 0` | 범위 밖 → 버림 |
| `arrive_home: "저녁쯤"` | 형식 아님 → 버림 |
| `avoid: "새우"` (문자열) | 목록이 아님 → 버림 |
| 모르는 항목 | 버림 |

설명에서도 마찬가지다. 답에 있는 수를 실행 결과와 대조해, **결과에 없는
수가 섞이면 표시한다** — "12분 걸립니다" 를 지어내면 사용자가 그것을
믿기 때문이다.

그리고 알레르기처럼 **틀리면 위험한 항목**은 읽었다는 사실만 남기고
사람에게 확인을 요청한다. 씽큐 클로의 "실행은 사람이 승인" 과 같은 자리다.

### 키가 없어도 검증된다

`ask` 는 `(프롬프트) -> 문자열` 함수이고 **주입받는다.** 스킬이 관측·조작
함수를 주입받는 것과 같은 구조다.

```
API 키 있음   → anthropic SDK 로 부른다
API 키 없음   → **설치된 claude CLI 로 부른다**   ← 이 환경이 여기다
둘 다 없음    → 규칙으로 읽는다
검사          → 가짜 LLM 을 넣어 결정적으로 시험 (22/22)
              → `--live` 를 주면 진짜로 부른다 (25/25)
```

처음에는 "API 키가 없어 이 경로는 검증 못 한다" 고 적었다. **틀렸다.**
환경을 실제로 보니 키는 없어도 `claude` CLI 가 깔려 있었다. 없다고
적기 전에 찾아봤어야 했다(2026-09-15 에 같은 실수를 기록해 두었다).

진짜로 불러 확인한 것:

| | 규칙으로 읽음 | LLM 으로 읽음 |
|---|---|---|
| 읽은 상황 | 19:00 · 45분 | 19:00 · 45분 |
| 가전 순서 | inventory→…→converge | **같음** |
| 개입 / 가열 / 질량비 | 0회 · 5.5분 · 0.78 | **0회 · 5.5분 · 0.78** |
| 설명의 지어낸 수 | — | **0개** |

CLI 를 부를 때 두 가지를 조심해야 했고, 둘 다 처음에 놓쳐서 엉뚱한
답이 왔다.

* 프롬프트를 **stdin 으로** 넘긴다. 명령줄 인자로 주면 Windows shell
  인용 규칙 때문에 개행에서 잘린다 — "'아래는' 에서 끊겨 들어왔습니다"
  라는 답이 돌아왔다.
* **빈 디렉토리에서 시스템 프롬프트를 덮어써서** 부른다. 그냥 부르면
  CLI 가 사용자의 `CLAUDE.md` 를 읽고 그 규칙대로 조언한다 — 실제로
  "CLAUDE.md 규칙대로 #local 채널에 알림을 보내려 했지만" 같은 문장과
  이번 실행에 없는 숫자(25·27·48)가 섞여 왔다. **그 숫자는 우리
  검증기가 잡아냈다.**

## 실측이 없는 상수를 다루는 법 — 교반 상수

`STIR_RELIEF`(저으면 눌어붙음이 이 비율로 준다)는 **실측이 없는 가정값**인데
결과를 가장 크게 움직였다. 0.55 를 0.66 으로 올리면 눌어붙음이 0.5404 에서
0.6066 이 되어 **세척 코스가 표준에서 강력으로 뒤집혔다 — 물 11.0L 에서
16.0L 로.**

먼저 실측을 찾았다. 열교환기 fouling 문헌은 유속이 높을수록 부착이 준다는
것을 말하지만 정량값이 가정 조리 조건과 맞지 않았고, 구체적 수치가 나온
곳은 출처가 분명하지 않은 블로그였다. **그런 값을 근거로 삼으면 "가정"
이라고 정직하게 적힌 것을 "문헌 근거" 로 포장하는 셈이라 지금보다 나쁘다.**

그래서 값을 지어내는 대신 **모른다는 사실을 값에 실었다.**

```
교반이 덜어낸 몫  × STIR_RELIEF_UNCERTAINTY(±20%)  →  soil_sigma 에 합성
aftercare 는 그 분포로 코스별 기대 비용을 최소화해 고른다
```

| `STIR_RELIEF` | 눌어붙음 | 불확실폭 | 코스 | 물 |
|---|---|---|---|---|
| 0.44 | 0.4631 | ±0.1585 | 표준 | 11.0L |
| 0.55 (현재) | 0.5404 | ±0.1275 | 표준 | 11.0L |
| 0.66 | 0.6066 | ±0.0966 | 표준 | 11.0L |

상수를 ±20% 흔들어도 **출하물(코스·물)이 바뀌지 않는다.** 민감도 검사에서
이 항목은 66.2% 에서 **0.00%** 가 됐다.

남은 사실은 숨기지 않는다. **눌어붙음 점수 자체는 여전히 상수에 흔들린다**
(0.4631~0.6066). 점수를 그대로 인용할 때는 이 폭을 함께 말해야 한다.
안정된 것은 그 점수로 내리는 **결정**이다.

## 무엇이 진짜이고 무엇이 대체인가

| 구성 | 상태 |
|---|---|
| 설계 루프 · 플래너 · 스킬 레지스트리 | **진짜** — 키 없이 동작 |
| 계획 계산 (전제조건 역추적 + 위상 정렬) | **진짜** — `planner.py` |
| 시나리오–실행 대조 검증 | **진짜** — 장면마다 `verified_by` 스킬 로그 확인 |
| 기기 API 규격 | **진짜** — ThinQ Connect 로 교체 가능한 형태 |
| 자료 수집 (`recipe_source`) | **진짜** — 식약처 공개 API 실호출, 100건 캐시 |
| 기기 내부 동작 | **시뮬레이터** — 증발·건조는 단순 1차 모델, 실측 아님 |
| 열 모델 | **열량 수지** — 투입·방열·잠열로 계산. 상수는 두 가지 실제 값에서 역산한 가정 |
| 흡수·거품·익힘 계수 | **가정** — 일반적인 조리 자료 범위에서 잡았고 실측이 아니다 |
| 끓는점 상승 | **없음** — 염도 자료가 없어 넣지 않았다 (졸수록 농도가 올라 실제로는 오른다) |
| 냄비 안 온도 분포 | **없음** — 온도가 하나뿐이라 "젓지 않으면 바닥이 탄다" 를 온도로 표현하지 못한다 |
| 고기가 익으며 내는 물 | **없음** — 채소 방출은 시작 시 더하는데 고기는 조리 중에 나온다 |
| 공개 레시피 100건 | **실제 공공 자료** (식약처 COOKRCP01) |
| 개인 조리 기록 3건 | **합성 데이터** — 실측 교체 필요 |
| 공개 레시피의 목표 질량비 | **가정** — 조리법별 기본값, 첫 조리 실측으로 대체되는 구조 |
| 눌어붙음(오염도) | **조리 중 실측** — 시뮬레이터 모델이며 실측 센서값은 아님 |
| LLM 기반 계획 (`agent.py`) | **미검증** — 현재 제출 경로가 아니다 |
| 자연어 읽기·장면 제안 (`thinq.py`·`llm_design.py`) | **진짜 LLM 으로 확인** — claude CLI 호출, 원문은 `fixtures/` 에 남겨 키 없이 재생 |
| 장보기 상점 (`store.py`) | **시뮬레이터** — 공개 레시피 재료에서 고른 236품목, **분류별 합성 가격**. 주류는 주세법상 온라인 판매 금지라 넣지 않았다. 즉시배송이 안 파는 것(한약재·특산품)은 **가정**이며 결과가 이것에 민감하다(찹쌀). 즉시배송 20분도 가정이다 — B마트는 "1시간 내" 를 내건다 |

## 비용과 키

제출 경로(`run_design.py`)는 **표준 라이브러리만** 쓴다. `pip install` 대상 0개, 유료 API 0개.

| 항목 | 키 | 비용 |
|---|---|---|
| 실행 전체 | 불필요 | 0원 |
| 식약처 레시피 DB | 공개 `sample` 키로 동작 / 발급키는 무료 | 0원 |
| ThinQ Connect | 교체 경로로만 문서화, 현재 미사용 | — |
| Claude API | `agent.py` 전용, 제출 경로 아님 | (유료, 미사용) |

## 산출물

- `AGENT_정의서.md` — 역할·사용자·Input/Process/Output
- `재사용_방안.md` — 실증/구조/설계 3등급으로 구분

산출물은 저장소에 함께 둔다 — 실행하지 않고도 결과를 볼 수 있어야 하기 때문이다.
대신 **코드를 고치면 다시 돌려야 한다.** `check_consistency.py` 가 산출물이
코드보다 오래됐는지 확인한다(실제로 `variance.json` 이 79분 낡은 채 있었다).
- `data/recipes.json` — 수집한 공개 자료 (출처·인증 방식 기록 포함)

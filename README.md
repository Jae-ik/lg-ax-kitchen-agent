# UX 시나리오 설계 Agent

**팀 독립선언문 · LG전자–국립창원대 AX 해커톤 Theme B (UX/UI 시나리오 설계자)**

고객 상황을 입력하면 **UX 시나리오를 생성하고, 그것을 실제로 실행해 검증한다.**
지시를 받아 가전을 돌리는 것이 아니라, 시나리오 설계라는 **직무를 반복 수행한다.**

```
입력: 고객 상황          출력: UX 시나리오 + 실행 결과
Goal → Plan → Tool·Skill → Execute → Evaluate → Output
```

## 실행

```bash
python run_design.py            # 고객 상황 4건 → 시나리오 4건 (주 산출물)
python run_design.py p1_야근    # 한 상황만
python run_demo.py              # 실행 층만 단독 — 스킬 재사용 실증
python run_repeat.py            # 같은 상황 두 번 — 기록이 다음 목표가 되는지
python run_share.py             # 본가 기록을 자취방·원룸 기기로 이식
python stress_test.py           # 일부러 망가뜨린 입력 19건
python check_regression.py      # scenarios.json 회귀 검사
python check_consistency.py     # 선언·물리·문서·맞물림·주장 11항목 검사
```

API 키가 없어도 전부 동작한다. 계획은 LLM이 아니라 **전제조건 플래너**가 계산한다.

**설계 층은 실행 층을 import 하지 않는다.** 실행 함수를 주입받는다.

## 핵심 결과

상황이 다르면 **계획 자체가 달라진다.** 순서는 코드 어디에도 적혀 있지 않다.

조리량·가열 시간·세척 코스가 상황마다 다른 것은 **가구원 수와 그 집 냄비**가
다르기 때문이다.

| 상황 | 조리량 | 가열 | 세척 | 기대 물 | 기본 대비 | 손이 가는 일 |
|---|---|---|---|---|---|---|
| 야근 1인 | 2인분 기록 → 1인분 | 5.6분 | 에코 | 8.3L | **−3.5L** | 3회 / 조리 5.6분 |
| 맞벌이 2인 | 그대로 2인분 | 7.85분 | 표준 | 11.8L | 0L | 3회 / 7.85분 |
| 알레르기 4인 | 공개 1인분 → 4배 | 21.25분 | 강력 | 16.8L | **−1.4L** | 5회 / 21.25분 |
| 퇴근길 1인 | 2인분 기록 → 1인분 | 5.5분 | 에코 | 8.3L | **−3.5L** | 3회 / 5.5분 |

물 절감은 **기본 코스가 틀렸을 때만** 생긴다. 4상황 평균 2.1L 이며,
요리와 양이 달라지면 이 값도 달라진다.

| 고객 상황 | 계산된 가전 작업 순서 | 선택 메뉴 | 개입 | 장면 |
|---|---|---|---|---|
| 야근 1인 가구 | inventory → recipe_source → menu → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 4/4 |
| 맞벌이 2인 가구 | … → **procure** → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 4/4 |
| 알레르기 4인 가구 | … → **procure** → prep → converge → aftercare | 호박잎 삼계탕 (**공개 레시피**) | 2회 | 5/5 |
| 퇴근길 1인 가구 | … → **procure**(선제) → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 4/4 |

1인 가구는 귀가 후 25분뿐이라 조달(20분 예상)이 예산을 넘는다.
Agent가 `stock_complete`를 이미 성립한 사실로 두자 플래너가 **`procure`를 스스로 제외**했다.
알레르기 가구는 저장 기록에 쓸 것이 없어 **공개 레시피 48건 중에서** 임박한 닭고기를 쓰는 것을 골랐고,
자동 주문하지 않고 물은 것이 2건이다 — 찹쌀은 제때 오는 상점이 없고(최속 720분 > 남은 60분), 미나리는 처음 사는 품목이다(개입 2회 = 설계된 정지).
퇴근길 가구는 **퇴근 시각을 알기 때문에** 이동 40분 안에 배송이 끝난다 —
냉장고와 양념 선반을 함께 확인해 두부·참기름을 귀가 시각에 맞춰 주문하고, 개입은 0회다.

## 두 번째 조리는 달라진다

```bash
python run_repeat.py            # 기본 p3_알레르기
```

| | 쓴 기록 | 목표 질량비 | 출처 | 가열 | 먹기 직전 |
|---|---|---|---|---|---|
| 1회차 | `pub_639` | 0.85 | 조리법 기본값(가정) | 21.25분 | 0.8500 |
| 2회차 | **`rec_004`** | 0.85 | **실측 기록** | 21.35분 | 0.8497 |

목표값 자체는 같다 — 1회차가 목표를 정확히 맞췄기 때문이다. 바뀐 것은
**출처**다. 가정값이 내 주방에서 나온 실측으로 대체됐고, 그때부터 같은 값이
유지된다(목표는 새 정보가 있을 때만 갱신한다).

조리가 끝나면 이번 실측이 기록으로 저장되고, 다음 번 목표가 된다.
공개 레시피의 가정값을 **내 주방에서 나온 값**이 대신한다.


| | 초기 질량 | 목표 | 도달 시간 | 먹기 직전 |
|---|---|---|---|---|
| 본가 6인용 | 618g | 0.78 | **7.7분** | 0.7799 |
| 자취방 2인용 | 206g | 0.78 | **3.4분** | 0.7800 |
| 원룸 1인용 | 103g | 0.78 | **2.35분** | 0.7800 |

가져간 것은 **목표 질량비**(비율이라 용량 무관), 줄인 것은 재료량, 버린 것은 **조리 시간**이다.
시간을 복사했다면 작은 냄비는 7.7분에 크게 지나쳤을 것이다.

**용량 비율은 코드 어디에도 적혀 있지 않다.** 기기가 자기 제원(인분·용량)을 알고 있고,
`record_import` 가 두 기기의 제원에서 비율을 계산한다 — 냄비가 바뀌면 기기 이름만 달라진다.
등록되지 않은 기기는 추측하지 않고 비율 1 로 두면서 "제원을 모른다" 고 말한다.

## 요리로서 챙긴 것

질량비 하나만 쫓으면 그건 "액체 졸이기" 지 요리가 아니다. 제안서가 적어 둔
것 중 코드에 없던 것과, 요리라면 당연한 것을 넣었다.

| 무엇 | 왜 | 결과 |
|---|---|---|
| **조리 단계(중간 투입)** | 두부를 처음부터 넣으면 부서진다. 제안서는 "재료 투입 전후를 구분한다" 고 적었는데 코드엔 없었다 | 질량비 0.93 에서 투입, 온도 **30도 하강** 후 재가열. 기준을 다시 잡아 진행률·ETA 가 무너지지 않는다 |
| **여열** | 숙련자는 목표에 닿고 나서 끄지 않는다. 미리 끈다 | 기기가 자기 여열을 예측(오차 0.37g)하고, 제어기가 그만큼 앞당겨 끈다. 모자라면 **다시 켜고** 예측 신뢰도를 낮춘다 |
| **몇 인분인가** | 4인 가구가 1인분(237g)을 조리하고 있었다. 가구원 수는 '세척까지 할지' 에만 쓰였다 | 기록의 인분 수와 가구원 수로 조리량을 정하고, **기기 용량이 상한**이 된다 |
| **끓어넘침 감지** | 제안서는 "가열 상한, 이상 감지" 를 약속했는데 상한(화력 5)만 있었다. 상한은 사양이지 상황 판단이 아니다 | 채움 비율 × 끓음 × 화력으로 위험을 재고 화력을 묶는다. 위험이 지나가면 **되돌린다** |

### 요리 중에 실제로 일어나는 일들

| 무엇 | 왜 중요한가 | 확인한 값 |
|---|---|---|
| **물을 먹는 재료** | 찹쌀 400g 은 국물을 800g 먹는다. 총 질량은 그대로라 **질량비만 보면 아무 일도 없어 보인다** | 물을 안 채우면 0.9336 에서 국물이 바닥나고 눌어붙음 1.0 |
| **물은 얼마나** | 흡수량만 채우면 졸일 물이 없다. `M ≥ (고형+흡수)/목표비율` | 삼계탕에 1088g 을 더 붓는다 |
| **뚜껑** | 덮으면 증기가 갇혀 더 높은 온도까지 오르고, 열면 증발이 급등한다 | 6분 뒤 **열면 78.5도 / 덮으면 97.0도** |
| **거품 걷기** | 질량이 주는데 **증발이 아니다.** 분모에서 빼지 않으면 졸은 것으로 샌다 | 1000g → 955g, 비율은 1.0 그대로 |
| **젓기** | 안 저으면 바닥이 눌어붙는다. 교반은 사람이 하는 일(제안서 표1)이라 **안내**한다 | 눌어붙음 0.092 → **0.0506** |
| **물로 되돌리기** | 졸이는 것은 되돌릴 수 없다고 가정했지만, 물을 부으면 된다 — 다만 묽어진다 | 오차 0.0242 → **0.0000**, 국물 3.1% 묽어짐 |

되돌리기는 **여열이 끝난 뒤**에 해야 한다. 불 끈 시점에 맞춰 부으면 남은 열로
다시 졸아든다. 그리고 묽어짐이 6% 를 넘으면 되돌리지 않고 지나친 채로 알린다.

### 누가 요리하는가 — 로봇이 아니다

제안서 표1 은 **"재료 손질·계량·투입, 필요 시 교반"을 사람 몫**으로,
"가열 제어 또는 조절 안내"를 시스템 몫으로 적었다. 그런데 코드는 투입·뚜껑·
거품까지 스스로 하면서 **"개입 0회"라고 보고**하고 있었다. 로봇이 아닌데
로봇처럼 굴었다.

가전이 실제로 할 수 있는 것은 **화력 조절과 판단·기록**뿐이다. 나머지는
사람의 손이 필요하고, 에이전트의 값은 그것을 **대신 하는 것이 아니라
언제 해야 하는지 정확히 알려주는 것**이다.

| 상황 | 손이 가는 일 | 냄비 앞에 있어야 하는 시간 |
|---|---|---|
| 야근 1인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 5.6분 |
| 맞벌이 2인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 7.85분 |
| 알레르기 4인 | 5회 (뚜껑 2, 거품 1, 교반 2) | **5분** / 조리 21.25분 |
| 퇴근길 1인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 5.5분 |

에이전트가 없으면 **언제 해야 할지 모르므로 조리 내내 지켜봐야 한다.**
그러니 값은 "개입 0회"가 아니라 **"지켜보는 시간이 21.25분에서 5분으로"** 다.
상황에 따라 조리 시간의 **24~55%** 이며, 양이 많고 오래 끓일수록 비율이 낮다
(4인분 24% / 1인분 54%) — 손이 가는 횟수는 비슷한데 조리가 길기 때문이다.
`user_touches`(되돌릴 수 없는 결정에 대한 확인 요청)와 `hands_on`(손이 가는
일)은 다른 지표이며, 둘을 나눠 보고한다.

### 열 모델 — 1차 지연에서 열량 수지로

예전에는 온도를 `T += (목표온도 - T) * k` 로 밀었다. 그러면 두 가지가 틀린다.

- 양이 달라도 데우는 시간이 같다 (310g 과 2000g 이 둘 다 3.75분)
- 출발 온도 차이가 지수적으로 사라진다 (냉장 재료를 넣으나 마나)

실제 화구는 **일정한 열량**을 넣는다. 온도는 열량 수지로 정해지고, 끓는점에
닿으면 남는 열은 온도가 아니라 **증발**로 간다.

| | 고친 뒤 |
|---|---|
| 310g / 620g / 2000g 끓기까지 | **2.0 / 3.25 / 8.25분** (양에 비례) |
| 20도 출발 vs 6도 출발 | **3.25분 vs 3.75분** (차이가 유지된다) |
| 화력 3 끓는 중 증발 | 20.9 g/분 |
| 여열 예측 오차 | **0.01g** (예측 3.29 / 실제 3.30) |

여열 구간은 **"불 끄고 상에 올리기까지 3분"** 으로 정의했다. 열량 수지로
바꾸자 끓음이 멎은 뒤에도 표면 증발이 계속돼 **끝나는 지점이 사라졌기**
때문이다(15분 두면 11.3g). 여열은 물리 현상이지만 "얼마나 두는가" 는
사람의 행동이라 명시해야 한다.

그리고 `converge` 는 **불을 끄는 시점까지만** 담당한다. 끈 뒤의 여열까지
붙들고 있으면 호출자가 다시 여열을 돌릴 때 **두 번 적용**된다 —
실제로 그래서 여열을 쓰는 쪽 오차가 더 컸다(0.0084 → 고친 뒤 0.0031).

상수는 두 가지 실제 값에서 역산했다 — 620g 을 불 끄면 100→90도가 약 3분
(방열 2.28 W/K), 화력 3 으로 20→100도가 약 5.5분(화력당 298 W).
둘 다 가정이며 실측으로 교체해야 하는 자리다.

### 시간이 맞는가 — 제안의 핵심 주장인데 검증하는 곳이 없었다

"귀가 후 25분 안에 제대로 된 한 끼" 가 제안의 주장인데, 검증은 장면 달성과
개입 횟수만 보고 있었다. 그리고 **주문한 재료가 도착하기 전에 조리를
시작하고 있었다** — "20분 뒤 도착" 이라 해놓고 주문 즉시 재고에 넣었다.

| 상황 | 조달 | 식사까지 | 예산 |
|---|---|---|---|
| 야근 1인 | 없음 | 14.6분 | 25분 |
| 맞벌이 2인 | 주문 후 **20분 대기** | 36.9분 | 45분 |
| 알레르기 4인 | 확인 요청 2건 | 30.2분 | 60분 |
| 퇴근길 1인 | **이동 중 도착** | 14.5분 | 25분 |

맞벌이와 퇴근길은 같은 메뉴인데 **22.4분 차이**가 난다. 그 전부가 배송을
기다리는 시간이고, 퇴근 시각을 알면 그 시간이 이동에 묻힌다.
이것이 선제 주문의 값이다 — 이제 숫자로 나온다.

### 익힘과 졸임은 다른 조건이다

제안서는 "익힘·졸임의 판단이 어려운" 사용자를 대상으로 적었는데 코드에는
졸임만 있었다. 질량비가 목표에 닿아도 닭고기가 안 익었으면 끝이 아니다.

`converge` 는 완료 조건을 둘 이상 가질 수 있다. 졸임이 먼저 끝나면
**화력을 유지하며 익을 때까지 기다리고**, 그 사이 더 졸면 물로 되돌린다.
유지 화력을 1 로 두었더니 53도로 식어 익지 않았다 — 3 이어야 한다.

### 요리 물리에서 찾은 모순

기능이 도는 것과 물리가 맞는 것은 다르다. 값을 하나씩 찔러 보고 찾았다.

| 무엇 | 증거 | 고친 것 |
|---|---|---|
| **찬물을 부어도 온도가 그대로** | 50g 부었는데 100.0 → 100.0도 | 재료 투입과 같은 질량가중 평균 (8.5도 하강) |
| **냄비를 넘겨도 말이 없다** | 1000g 냄비에 1200g(120%) | 투입 시 채움 비율을 보고 경고 |
| **늦게 넣은 재료가 이미 익어 있다** | 8분에 넣은 고기가 0분부터 익은 것으로 | 요구량을 늘려 덜 익은 것으로 본다 |
| **뚜껑이 넘침과 무관** | 덮으나 여나 위험 0.78 | 거품이 갇히므로 1.6배 (0.78 → 1.0) |
| **거품을 걷으면 국물이 준다** | 걷은 50g 이 전부 국물에서 빠짐 | 거품은 단백질·기름이다 — 고형분에서 80% |

### 여열 보정은 언제 이득인가 — 재보고 정했다

"미리 끄면 더 정확하다" 는 그럴듯하지만 항상 참이 아니다. 120시드로 쟀다.

| 관측 주기 하한 | 여열 보정 끔 | 여열 보정 켬 |
|---|---|---|
| 0.1분 | **0.0030** | 0.0052 |
| 0.5분 | 0.0062 | **0.0052** |
| 1.0분 | 0.0135 | **0.0049** |

관측을 자주 할 수 있으면 목표 바로 앞까지 잘게 다가가면 되고, 그때 여열을
미리 빼는 것은 **예측 오차를 들여오는 일**이다. 관측이 드물면 반대다.
그래서 `converge` 는 **한 걸음의 크기와 여열 크기를 비교해 스스로 정한다.**

## 흔들림 측정

```bash
python measure_variance.py 500 200   # → variance.json
```

단일 실행 수치를 근거로 쓰지 않으려고 시드를 바꿔 반복했다.

| | 결과 |
|---|---|
| 조리기 가열 시간 | 200회 중앙 **7.6분** (7.35~7.9, 표준편차 0.105) |
| 건조기 건조 시간 | 200회 중앙 **11.4분** (11.0~11.75, 표준편차 0.153) |
| 계획 순서·선택 메뉴·세척 코스·확인 요청·장면 | 160회(40×4상황) **전부 불변** |
| 조리기 최종 질량비 | **0.7775~0.7851** — 목표 0.78 **양옆으로** 최대 0.005 |
| 건조기 최종 함수율 | 0.0789~0.0800 |

여열을 예측해 미리 끄면서 오차가 **한쪽(늘 더 졸음)에서 양쪽으로** 바뀌었다.
편향이 사라졌다는 뜻이고, 그래서 이번 실측을 다음 목표로 저장해도 흘러가지 않는다.

관측 주기를 1분 고정에서 **목표까지 남은 시간에 맞춰 줄이도록** 바꾸고
(ETA 를 1.4배 보수적으로 본다 — 졸이기는 가속하기 때문이다),
지나치는 폭이 0.0505 → 0.0082 로 줄었다.

## 무엇이 진짜이고 무엇이 대체인가

| 구성 | 상태 |
|---|---|
| 설계 루프 · 플래너 · 스킬 레지스트리 | **진짜** — 키 없이 동작 |
| 계획 계산 (전제조건 역추적 + 위상 정렬) | **진짜** — `planner.py` |
| 시나리오–실행 대조 검증 | **진짜** — 장면마다 `verified_by` 스킬 로그 확인 |
| 기기 API 규격 | **진짜** — ThinQ Connect 로 교체 가능한 형태 |
| 자료 수집 (`recipe_source`) | **진짜** — 식약처 공개 API 실호출, 100건 캐시 |
| 기기 내부 동작 | **시뮬레이터** — 증발·건조는 단순 1차 모델, 실측 아님 |
| 열 모델 | **열량 수지** — 투입·방열·잠열로 계산. 상수는 두 가지 실제 값에서 역산한 가정 |
| 흡수·거품·익힘 계수 | **가정** — 일반적인 조리 자료 범위에서 잡았고 실측이 아니다 |
| 끓는점 상승 | **없음** — 염도 자료가 없어 넣지 않았다 (졸수록 농도가 올라 실제로는 오른다) |
| 냄비 안 온도 분포 | **없음** — 온도가 하나뿐이라 "젓지 않으면 바닥이 탄다" 를 온도로 표현하지 못한다 |
| 고기가 익으며 내는 물 | **없음** — 채소 방출은 시작 시 더하는데 고기는 조리 중에 나온다 |
| 공개 레시피 100건 | **실제 공공 자료** (식약처 COOKRCP01) |
| 개인 조리 기록 3건 | **합성 데이터** — 실측 교체 필요 |
| 공개 레시피의 목표 질량비 | **가정** — 조리법별 기본값, 첫 조리 실측으로 대체되는 구조 |
| 눌어붙음(오염도) | **조리 중 실측** — 시뮬레이터 모델이며 실측 센서값은 아님 |
| LLM 기반 계획 (`agent.py`) | **미검증** — API 키 없음. 현재 제출 경로가 아니다 |

## 비용과 키

제출 경로(`run_design.py`)는 **표준 라이브러리만** 쓴다. `pip install` 대상 0개, 유료 API 0개.

| 항목 | 키 | 비용 |
|---|---|---|
| 실행 전체 | 불필요 | 0원 |
| 식약처 레시피 DB | 공개 `sample` 키로 동작 / 발급키는 무료 | 0원 |
| ThinQ Connect | 교체 경로로만 문서화, 현재 미사용 | — |
| Claude API | `agent.py` 전용, 제출 경로 아님 | (유료, 미사용) |

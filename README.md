# UX 시나리오 설계 Agent

**팀 독립선언문 · LG전자–국립창원대 AX 해커톤 Theme B (UX/UI 시나리오 설계자)**

고객 상황을 입력하면 **UX 시나리오를 생성하고, 그것을 실제로 실행해 검증한다.**
지시를 받아 가전을 돌리는 것이 아니라, 시나리오 설계라는 **직무를 반복 수행한다.**

```
입력: 고객 상황          출력: UX 시나리오 + 실행 결과
Goal → Plan → Tool·Skill → Execute → Evaluate → Output
```

## 실행

```bash
python run_design.py            # 고객 상황 4건 → 시나리오 4건 (주 산출물)
python run_design.py p1_야근    # 한 상황만
python run_demo.py              # 실행 층만 단독 — 스킬 재사용 실증
python run_repeat.py            # 같은 상황 두 번 — 기록이 다음 목표가 되는지
python run_share.py             # 본가 기록을 자취방·원룸 기기로 이식
python stress_test.py           # 일부러 망가뜨린 입력 19건
python thinq.py "오늘 늦어. 9시 반 도착이고 배추랑 두부 있어"   # 자연어로 받기

python check_all.py             # ← 전부 돌린다. 실패하면 무엇부터 볼지 알려준다
python check_all.py --fast      #   분산 측정(200회)을 건너뛴다

python check_regression.py      # scenarios.json 회귀 검사
python check_consistency.py     # 선언·물리·문서·맞물림·주장 11항목 검사
python check_interlock.py       # 스킬 절단 실험 — 각 단계가 뒤에 실제로 영향을 주는가
python check_generalize.py      # 설계하지 않은 상황 5종에서도 이유를 남기고 끝나는가
python check_skills.py          # 스킬 11종 단독 — 순수성·경계값·근거·정직성·격리·계약
python check_reuse.py           # reusable_for 가 말뿐인지 — 주방 밖 8개 대상에 실제 적용
python check_planner.py         # 순서를 정말 계산하는가 — 결정성·최소성·순환·한계
python check_physics.py         # 무작위 조작 불변량 + 에너지 수지·끓는점·규모·뚜껑 정량 검산
python check_cooking.py         # 조리 상식이 코드에서 성립하는가 (14항목)
python check_sensitivity.py     # 어느 상수가 결과를 지배하는가 (가정값 감시)
```

API 키가 없어도 전부 동작한다. 계획은 LLM이 아니라 **전제조건 플래너**가 계산한다.

## 핵심 결과

상황이 다르면 **계획 자체가 달라진다.** 순서는 코드 어디에도 적혀 있지 않다.

조리량·가열 시간·세척 코스가 상황마다 다른 것은 **가구원 수와 그 집 냄비**가
다르기 때문이다.

| 상황 | 조리량 | 가열 | 세척 | 기대 물 | 기본 대비 | 손이 가는 일 |
|---|---|---|---|---|---|---|
| 야근 1인 | 2인분 기록 → 1인분 | 5.5분 | 에코 | 8.3L | **−3.5L** | 3회 / 조리 5.5분 |
| 맞벌이 2인 | 그대로 2인분 | 7.75분 | 표준 | 11.8L | 0L | 3회 / 7.75분 |
| 알레르기 4인 | 공개 1인분 → 4배 | 28.25분 | 강력 | 16.8L | **−1.4L** | 6회 / 28.25분 |
| 퇴근길 1인 | 2인분 기록 → 1인분 | 5.5분 | 에코 | 8.3L | **−3.5L** | 3회 / 5.5분 |

물 절감은 **기본 코스가 틀렸을 때만** 생긴다. 4상황 평균 2.1L 이며,
요리와 양이 달라지면 이 값도 달라진다.

| 고객 상황 | 계산된 가전 작업 순서 | 선택 메뉴 | 개입 | 장면 |
|---|---|---|---|---|
| 야근 1인 가구 | inventory → recipe_source → menu → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 4/4 |
| 맞벌이 2인 가구 | … → **procure**(선제) → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 5/5 |
| 알레르기 4인 가구 | … → **procure**(선제) → prep → converge → aftercare | 호박잎 삼계탕 (**공개 레시피**) | 2회 | 7/7 |
| 퇴근길 1인 가구 | … → **procure**(선제) → prep → converge → aftercare | 된장찌개 (저장 기록) | 0회 | 5/5 |

1인 가구는 귀가 후 25분뿐이라 조달(즉시배송 27분)이 예산을 넘는다.
Agent가 `stock_complete`를 이미 성립한 사실로 두자 플래너가 **`procure`를 스스로 제외**했다.
**퇴근 시각을 아는 가구는 현관에 들어서기 전에 끝낸다.** 퇴근길에 메시지로 오늘 메뉴를
알리고, 처음 사는 것처럼 판단이 안 되는 것만 물어 승인받고, 주문한 것은 이동 중에 도착한다.
씽큐 클로의 "제안 → 사람 승인 → 실행" 이 이 자리다. 퇴근 이동은 37분으로 뒀다 — 통계청
「2024년 통근 근로자 이동 특성 분석」의 출퇴근 왕복 평균 73.9분의 절반이다(편도만 따로는
확인하지 못했다). 야근 1인은 출발 시각이 일정하지 않아 모른다고 두었다 — 그래서 귀가 뒤에
정하는 **대조군**이다. 퇴근할 때 알렸다면 어떻게 되는지는 아래 "주문 방식" 표에 있다
(9.5분 — 메뉴를 오는 길에 정한다).

알레르기 가구는 공개 레시피를 알레르기 25건·나트륨 27건 걸러 48건을 남기고, 그중
**끓이기**이면서 **오늘 안에 재료가 오는** 것 가운데 내일이면 버려야 할 닭고기(1일 남음)를
쓰는 호박잎 삼계탕을 골랐다. 처음 사는 찹쌀·미나리는 **퇴근길에 물어 승인받고**(개입 2회 =
설계된 정지) 이동 중에 받는다. 국물까지 끓여 식사까지 32.2분 / 예산 60분.

| 알레르기 4인 가구 | 퇴근 시각을 모를 때 | 퇴근 시각을 알 때 (지금) |
|---|---|---|
| 주문 | 귀가 후, 배송 27분을 집에서 기다림 | 퇴근길에 승인받아 이동 중 도착 |
| 삼계탕 | 국물까지 끓이면 64.2분 — 예산 초과 → **재계획으로 된장찌개** | 32.2분에 성립 |
| 닭고기(1일 남음) | "오늘 쓰는 메뉴가 없다 — 냉동을 권한다" | 오늘 쓴다 |
| 확인 요청 | 0회 | 2회(찹쌀·미나리, 퇴근길 메시지) |

맞벌이 가구도 퇴근 시각을 알면 11.8분, 모르면 재계획을 거쳐 43.8분이다.

> **고쳐 온 과정.** (9/28) 찹쌀을 "제때 오는 상점이 없다(720분)" 고 물어 놓고 승인을 가정해
> **그 자리에서 재고에 넣었다.** (9/29) 삼계탕이 **국물 80g · 눌어붙음 0.90** 으로 끝나고
> 있었다 — 공개 레시피에 물이 없어 흡수분과 졸일 만큼만 부었다. 국물을 남기자 귀가 후
> 주문으로는 60분을 넘었고(국물 1인분 75g 이하일 때만 안), **사용자가 "현관에 들어서기 전에
> 대화와 주문이 끝나 있어야 하지 않느냐" 고 짚어** 퇴근길 단계를 넣었다.
퇴근길 가구는 **퇴근 시각을 알기 때문에** 이동 40분 안에 배송이 끝난다 —
냉장고와 양념 선반을 함께 확인해 두부·참기름을 귀가 시각에 맞춰 주문하고, 개입은 0회다.

## 두 번째 조리는 달라진다

```bash
python run_repeat.py            # 기본 p3_알레르기
```

| | 쓴 기록 | 목표 질량비 | 출처 | 가열 | 먹기 직전 |
|---|---|---|---|---|---|
| 1회차 | `pub_639` | 0.85 | 조리법 기본값(가정) | 28.25분 | 0.85 |
| 2회차 | **`rec_004`** | 0.85 | **실측 기록** | 26.35분 | 0.85 |

1회차가 목표를 정확히 맞춰 값은 같지만 **출처가 바뀌었다** — 두 번째부터는 남의 평균이
아니라 내 주방에서 실제로 나온 값을 쫓는다(목표는 새 정보가 있을 때만 갱신한다).

조리가 끝나면 이번 실측이 기록으로 저장되고, 다음 번 목표가 된다.
공개 레시피의 가정값을 **내 주방에서 나온 값**이 대신한다.

```bash
python run_share.py
```

| | 초기 질량 | 목표 | 도달 시간 | 먹기 직전 |
|---|---|---|---|---|
| 본가 6인용 | 618g | 0.78 | **7.7분** | 0.7799 |
| 자취방 2인용 | 206g | 0.78 | **3.4분** | 0.7800 |
| 원룸 1인용 | 103g | 0.78 | **2.35분** | 0.7800 |

가져간 것은 **목표 질량비**(비율이라 용량 무관), 줄인 것은 재료량, 버린 것은 **조리 시간**이다.
시간을 복사했다면 작은 냄비는 7.7분에 크게 지나쳤을 것이다.

**용량 비율은 코드 어디에도 적혀 있지 않다.** 기기가 자기 제원(인분·용량)을 알고 있고,
`record_import` 가 두 기기의 제원에서 비율을 계산한다 — 냄비가 바뀌면 기기 이름만 달라진다.
등록되지 않은 기기는 추측하지 않고 비율 1 로 두면서 "제원을 모른다" 고 말한다.

## 요리로서 챙긴 것

질량비 하나만 쫓으면 그건 "액체 졸이기" 지 요리가 아니다. 제안서가 적어 둔
것 중 코드에 없던 것과, 요리라면 당연한 것을 넣었다.

| 무엇 | 왜 | 결과 |
|---|---|---|
| **조리 단계(중간 투입)** | 두부를 처음부터 넣으면 부서진다. 제안서는 "재료 투입 전후를 구분한다" 고 적었는데 코드엔 없었다 | 질량비 0.93 에서 투입, 온도 **30도 하강** 후 재가열. 기준을 다시 잡아 진행률·ETA 가 무너지지 않는다 |
| **여열** | 숙련자는 목표에 닿고 나서 끄지 않는다. 미리 끈다 | 기기가 자기 여열을 예측(오차 0.37g)하고, 제어기가 그만큼 앞당겨 끈다. 모자라면 **다시 켜고** 예측 신뢰도를 낮춘다 |
| **몇 인분인가** | 4인 가구가 1인분(237g)을 조리하고 있었다. 가구원 수는 '세척까지 할지' 에만 쓰였다 | 기록의 인분 수와 가구원 수로 조리량을 정하고, **기기 용량이 상한**이 된다 |
| **끓어넘침 감지** | 제안서는 "가열 상한, 이상 감지" 를 약속했는데 상한(화력 5)만 있었다. 상한은 사양이지 상황 판단이 아니다 | 채움 비율 × 끓음 × 화력으로 위험을 재고 화력을 묶는다. 위험이 지나가면 **되돌린다** |

### 요리 중에 실제로 일어나는 일들

| 무엇 | 왜 중요한가 | 확인한 값 |
|---|---|---|
| **물을 먹는 재료** | 찹쌀 400g 은 국물을 800g 먹는다. 총 질량은 그대로라 **질량비만 보면 아무 일도 없어 보인다** | 물을 안 채우면 0.9336 에서 국물이 바닥나고 눌어붙음 1.0 |
| **물은 얼마나** | 흡수량만 채우면 졸일 물이 없고, 졸일 만큼만 채우면 **끝났을 때 국물이 없다**. `M ≥ (고형+흡수+남길 국물)/목표비율` | 4인분 삼계탕: 흡수 800g + 남길 국물 500g → 1581g 을 붓고 국물 499g 으로 끝난다 |
| **뚜껑** | 덮으면 증기가 갇혀 더 높은 온도까지 오르고, 열면 증발이 급등한다 | 6분 뒤 **열면 78.5도 / 덮으면 97.0도** |
| **거품 걷기** | 질량이 주는데 **증발이 아니다.** 분모에서 빼지 않으면 졸은 것으로 샌다 | 1000g → 955g, 비율은 1.0 그대로 |
| **젓기** | 안 저으면 바닥이 눌어붙는다. 교반은 사람이 하는 일(제안서 표1)이라 **안내**한다 | 눌어붙음 0.092 → **0.0506** |
| **물로 되돌리기** | 졸이는 것은 되돌릴 수 없다고 가정했지만, 물을 부으면 된다 — 다만 묽어진다 | 오차 0.0242 → **0.0000**, 국물 3.1% 묽어짐 |

되돌리기는 **여열이 끝난 뒤**에 해야 한다. 불 끈 시점에 맞춰 부으면 남은 열로
다시 졸아든다. 그리고 묽어짐이 6% 를 넘으면 되돌리지 않고 지나친 채로 알린다.

### 누가 요리하는가 — 로봇이 아니다

제안서 표1 은 **"재료 손질·계량·투입, 필요 시 교반"을 사람 몫**으로,
"가열 제어 또는 조절 안내"를 시스템 몫으로 적었다. 그런데 코드는 투입·뚜껑·
거품까지 스스로 하면서 **"개입 0회"라고 보고**하고 있었다. 로봇이 아닌데
로봇처럼 굴었다.

가전이 실제로 할 수 있는 것은 **화력 조절과 판단·기록**뿐이다. 나머지는
사람의 손이 필요하고, 에이전트의 값은 그것을 **대신 하는 것이 아니라
언제 해야 하는지 정확히 알려주는 것**이다.

| 상황 | 손이 가는 일 | 냄비 앞에 있어야 하는 시간 |
|---|---|---|
| 야근 1인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 5.5분 |
| 맞벌이 2인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 7.75분 |
| 알레르기 4인 | 6회 (뚜껑 2, 거품 1, 교반 3) | **6분** / 조리 28.25분 |
| 퇴근길 1인 | 3회 (뚜껑 2, 투입 1) | **3분** / 조리 5.5분 |

에이전트가 없으면 **언제 해야 할지 모르므로 조리 내내 지켜봐야 한다.**
그러니 값은 "개입 0회"가 아니라 **"지켜보는 시간이 28.25분에서 6분으로"** 다.
상황에 따라 조리 시간의 **21~55%** 이며, 양이 많고 오래 끓일수록 비율이 낮다
(4인분 삼계탕 21% / 1인분 55%) — 손이 가는 횟수는 비슷한데 조리가 길기 때문이다.
`user_touches`(되돌릴 수 없는 결정에 대한 확인 요청)와 `hands_on`(손이 가는
일)은 다른 지표이며, 둘을 나눠 보고한다.

### 열 모델 — 1차 지연에서 열량 수지로

예전에는 온도를 `T += (목표온도 - T) * k` 로 밀었다. 그러면 두 가지가 틀린다.

- 양이 달라도 데우는 시간이 같다 (310g 과 2000g 이 둘 다 3.75분)
- 출발 온도 차이가 지수적으로 사라진다 (냉장 재료를 넣으나 마나)

실제 화구는 **일정한 열량**을 넣는다. 온도는 열량 수지로 정해지고, 끓는점에
닿으면 남는 열은 온도가 아니라 **증발**로 간다.

| | 고친 뒤 |
|---|---|
| 310g / 620g / 2000g 끓기까지 | **2.0 / 3.25 / 8.25분** (양에 비례) |
| 20도 출발 vs 6도 출발 | **3.25분 vs 3.75분** (차이가 유지된다) |
| 화력 3 끓는 중 증발 | 20.9 g/분 |
| 여열 예측 오차 | **0.01g** (예측 3.29 / 실제 3.30) |

여열 구간은 **"불 끄고 상에 올리기까지 3분"** 으로 정의했다. 열량 수지로
바꾸자 끓음이 멎은 뒤에도 표면 증발이 계속돼 **끝나는 지점이 사라졌기**
때문이다(15분 두면 11.3g). 여열은 물리 현상이지만 "얼마나 두는가" 는
사람의 행동이라 명시해야 한다.

그리고 `converge` 는 **불을 끄는 시점까지만** 담당한다. 끈 뒤의 여열까지
붙들고 있으면 호출자가 다시 여열을 돌릴 때 **두 번 적용**된다 —
실제로 그래서 여열을 쓰는 쪽 오차가 더 컸다(0.0084 → 고친 뒤 0.0031).

상수는 두 가지 실제 값에서 역산했다 — 620g 을 불 끄면 100→90도가 약 3분
(방열 2.28 W/K), 화력 3 으로 20→100도가 약 5.5분(화력당 298 W).
둘 다 가정이며 실측으로 교체해야 하는 자리다.

### 시간이 맞는가 — 제안의 핵심 주장인데 검증하는 곳이 없었다

"귀가 후 25분 안에 제대로 된 한 끼" 가 제안의 주장인데, 검증은 장면 달성과
개입 횟수만 보고 있었다. 그리고 **주문한 재료가 도착하기 전에 조리를
시작하고 있었다** — "20분 뒤 도착" 이라 해놓고 주문 즉시 재고에 넣었다.

| 상황 | 조달 | 식사까지 | 예산 |
|---|---|---|---|
| 야근 1인 | 없음 | 14.5분 | 25분 |
| 맞벌이 2인 | 퇴근길 주문, **이동 중 도착** | 11.8분 | 45분 |
| 알레르기 4인 | 퇴근길 승인 2건, **이동 중 도착** | 32.2분 | 60분 |
| 퇴근길 1인 | 퇴근길 주문, **이동 중 도착** | 9.5분 | 25분 |

선제 주문의 값은 **같은 가구로** 잰다. 맞벌이는 퇴근 시각을 모르면 43.8분(귀가 후 주문 ·
27분 대기 · 재계획), 알면 11.8분 — **32분 차이**다. 배송 대기가 이동에 묻히고, 재고 확인·
메뉴 결정(5분)도 집 밖에서 끝나기 때문이다. 식사까지는 이제 "귀가 뒤 집에서 쓴 시간" 이다.

장면 시각도 실행 뒤에 **실제 시각으로 다시 맞춘다**(`retime_beats`). 전에는 장면이 귀가
+45분 같은 고정값이라, 식사까지 48분 걸린 가구에서 **밥이 되기도 전에 세척기가 도는**
시나리오였다. 세척은 음식이 된 뒤 식사 시간(30분 — 통계청 2019 생활시간조사의 한 끼 25~39분
범위 안의 값)이 지나서 시작하고, 세척 실행의 소음
판단도 그 시각을 쓴다. 재계획·버림 알림·승인처럼 **실행 중에 에이전트가 스스로 한 판단**은
시나리오 끝에 "실행 중" 장면으로 남는다(`check_cooking` 이 세척은 식사 뒤·선제 주문은 귀가
전인지 본다).

### 재계획 — 막히면 원인을 진단하고, 풀 수 있는 결정만 푼다

실행이 막히거나 예산을 넘기면 되돌아간다. 두 층이 나눠 맡는다.

| 누가 | 하는 일 |
|---|---|
| 도메인 (`kitchen_domain.diagnose`) | 막힌 결과를 보고 **원인 목록**과, 원인마다 **풀 수 있는가**·풀면 제약이 어떻게 바뀌는가를 낸다 |
| 설계 층 (`run_design`) | 풀 수 있는 원인을 **하나씩** 풀어 시나리오부터 다시 짠다. 같은 원인은 두 번 풀지 않고 최대 3번. 끝나면 **시도들 중 가장 나은 안**을 고른다 |
| 플래너 | 바뀐 제약에서 **순서를 다시 계산**한다 — 조달을 되살리면 procure 가 스스로 다시 들어간다 |
| 실행 검증 | 예산을 넘는지 **실제 실행으로** 판정한다(추정이 아니라) |

| 원인 | 풀 수 있나 | 풀면 |
|---|---|---|
| 추정으로 조달을 뺐는데 재고로 만들 메뉴가 없다 | 예 | 조달을 되살린다 |
| 고른 메뉴가 뒤 단계(계량·조리)에서 막혔다 | 예 | 그 메뉴를 빼고 다시 고른다 |
| 고른 메뉴가 예산을 넘겼다 | 예 | 그 메뉴를 빼고 더 빨리 되는 것을 찾는다 |
| 알레르기·기피, 나트륨, 시간 예산, 기기가 못 하는 조리법 | **아니오** | 풀지 않는다 — 풀어서 성립시키면 고객을 바꾼 것이다 |

즉시배송이 45분이면(이동 37분 안에 못 받아 선제 주문이 안 된다) 알레르기 가구(예산 60분)가
실제로 밟는 과정이다.

| 시도 | 무엇을 풀었나 | 결과 |
|---|---|---|
| 1 | — (추정 68분 > 60분이라 조달을 뺌) | 재고로 만들 메뉴가 없어 멈춤 |
| 2 | 조달을 되살림 | 호박잎 삼계탕 82.2분 — 초과 |
| 3 | 삼계탕을 뺌 | 된장찌개(rec_001) 66.2분 — 초과 |
| 4 | rec_001 도 뺌 | 된장찌개(rec_002) **63.6분** — 초과 |

성립한 안이 없어 **가장 가까운 4번째 안(63.6분)** 을 고르고, 3.6분 넘는다고 그대로 보고한다.
재계획했다는 사실·이유·고른 안은 결과(`재계획`, `고른 안`)와 설명 문장에 남는다.

`check_generalize` 가 성질을 본다 — 필요할 때만 하는가(p1 은 0회), 같은 원인을 두 번
풀지 않는가, 고른 안이 시도 중 가장 나은가, 거의 모든 것에 알레르기인 가구에서도
**알레르기를 풀지 않는가**, 같은 입력이면 같은 재계획을 하는가.

**한계.** 원인 진단은 도메인에 적어 둔 규칙이다 — 에이전트가 "어느 결정이 원인인가"
를 스스로 추론하는 것은 아니다. 조리 **도중**(가열 중) 문제를 만나 다른 방법으로
바꾸는 재계획도 아니다 — 그것은 converge 안의 되먹임 제어가 맡는다.

처음엔 즉시배송을 **근거 없이 20분**으로 뒀다. 지금은 **27분**이다 — 배민 B마트의

### 주문 방식은 고객이 정한다 (9/30)

"퇴근길에 무조건 자동 주문" 은 승인 원칙(처음 사는 것·상한 초과는 묻는다)과 부딪히고,
"매번 상의" 는 개입만 늘린다. 그래서 **한 번 정해 두는 선호**로 받는다(`order_mode`).

| 방식 | 조달이 하는 일 | 사람이 하는 일 |
|---|---|---|
| `auto` | 산 적 있고 품목 상한(`auto_limit_krw`, 기본 15,000원)·**합계 상한**(`order_cap_krw`, 기본 30,000원, 가정) 안이면 주문, 나머지만 묻는다 | 물어본 것만 승인 |
| `ask` | 부족한 것을 모아 퇴근길 메시지로 묻고, 승인받은 것만 주문한다 | 품목마다 승인 |
| `self` | 주문하지 않고 **살 것 목록**만 보낸다 | 들러서 산다(퇴근길 +15분 · 집에서 +25분, **가정**) |

- **어느 방식이든 안 풀리는 것:** 처음 사는 품목·상한 초과·못 먹는 재료는 자동으로 사지 않는다
  (`ProcureSkill`). 못 먹는 재료는 `self` 의 목록에도 넣지 않는다.
- **정해 두지 않았으면 `ask`** — 돈을 쓰는 것은 되돌릴 수 없고, 모를 때의 기본값은 멈춤이다.
- **정해 둔 선호 < 그날 말.** `thinq.run(text, profile={"order_mode": "auto"})` 처럼 가구
  선호를 주면 그것을 쓰고, 그날 말이 있으면 그날 말이 이긴다 — **주문 방식만.** 돈·동의·가정값
  설정(상한·위치 동의 등)은 그날 말로 바뀌지 않는다(설정에서만). 알레르기는 가구가 **저장**하고
  그날 말은 더하기만 한다(10/1 고침 — 아래 "전수 점검").
- **그날 말로 바꾼다.** thinq 가 "오늘은 내가 마트 들를게" → `self`, "알아서 시켜" → `auto`,
  "물어보고 사" → `ask` 로 읽는다(LLM 이 있으면 LLM 이 읽고, 값은 세 가지 밖이면 버린다).
  LLM 은 방식을 **읽기만** 하고, 무엇을 살지·자동으로 살지는 조달 스킬이 정한다.
- 가구별 선호(가정): 야근 1인·맞벌이·퇴근길은 `auto`, 알레르기 가구는 못 먹는 것이 섞일까 봐
  `ask`.

같은 가구에서 방식과 퇴근 정보만 바꿔 잰 값(`python mode_sensitivity.py`, 식사까지 분 · 개입):

| 가구 | 퇴근 | auto | ask | self |
|---|---|---|---|---|
| 야근 1인 | 앎(알림) | 9.5 · 0 | 9.5 · 0 | 9.5 · 0 (살 것 없음) |
| | 모름 | 14.5 · 0 | 14.5 · 0 | 14.5 · 0 |
| 맞벌이 2인 | 앎 | 11.8 · 0 | 11.8 · 1 | 26.8 · 0 (두부) |
| | 모름 | 43.8 · 0 (재계획) | 43.8 · 1 (재계획) | 41.8 · 0 (재계획) |
| 알레르기 4인 | 앎 | 32.2 · 2 (삼계탕) | 32.2 · 2 (삼계탕) | 47.2 · 0 (찹쌀·미나리) |
| | 모름 | 48.1 · 0 (재계획 · 된장찌개) | 48.1 · 3 (재계획) | 46.1 · 0 (재계획) |
| 퇴근길 1인 | 앎 | 9.5 · 0 | 9.5 · 2 | 24.5 · 0 (재계획 · 두부·참기름) |
| | 모름 | 메뉴 못 정함 | 메뉴 못 정함 | 메뉴 못 정함 |

읽는 법:
- 야근 1인은 퇴근 시각을 모르는 가구(대조군)라, "앎(알림)" 은 **퇴근할 때 알렸다면** 이다
  (`leave_if_notified`). 알리면 메뉴를 오는 길에 정해 14.5 → 9.5분이다.
- **방식은 개입과 시간을 맞바꾼다.** `ask` 는 시간은 `auto` 와 같고 개입이 늘고, `self` 는
  개입이 0 이지만 들르는 시간(가정 15분)만큼 식사가 늦다. 어느 쪽이 나은지는 고객이 정할
  일이다 — 그래서 변수로 둔다.
- 알레르기 가구는 `auto` 와 `ask` 가 같다(개입 2). 부족한 두 품목이 **처음 사는 것**이라
  `auto` 에서도 어차피 묻기 때문이다.
- 퇴근 정보의 값은 방식과 무관하게 크다(맞벌이 11.8 → 43.8, 알레르기 삼계탕 → 재계획).
  퇴근길 1인은 퇴근 정보가 없으면 **어떤 방식으로도** 성립하지 않는다 — 예산 25분 안에
  두부를 받을 길(배송 27분 · 다녀오기 25분)이 없다.
- 들르는 시간 15·25분은 **확인하지 못한 가정**이다. 값을 바꾸면 `self` 열이 그만큼 움직인다.

### 퇴근을 무엇으로 아는가 — 메시지와 위치 (9/30)

선제 주문은 **언제 나서는지(퇴근 시각)와 집까지 몇 분(이동 시간)** 을 알아야 한다. 정해 둔
퇴근 시각이 없는 가구(야근)도 알 수 있게 두 길을 더했다.

| 알아내는 법 | 입력 | 확실성 | 퇴근길에 쓸 수 있는 시간 |
|---|---|---|---|
| 정해 둔 시각 | 가구 정보(`leave_office`) | 날마다 다르면 틀린다 | 이동 전부 |
| **그날 말** | "지금 퇴근해, 40분 걸려" (thinq, `now` 필요) | 확정 | 이동 전부 |
| **휴대폰 위치** | 회사 영역을 나섬 (`location.py`, 시뮬레이터) | 추정 — 점심·외근도 나선다 | 이동 − 확인 5분 |

- **믿는 순서: 그날 말 > 위치 > 정해 둔 시각.** 말이 있으면 위치는 보지 않는다.
- **위치는 셋을 모두 통과해야 퇴근으로 본다.** 위치 사용 동의(기본값: 안 씀) · 평소 퇴근
  시간대(기본 17:00~23:59, 점심 12:10 이탈 제외) · 나선 뒤 5분 안에 다시 들어오지 않음.
  5분을 기다린 뒤에야 판단하므로 그만큼 퇴근길 시간을 잃는다. 판단 시각까지의 이벤트만
  본다(그 뒤에 다시 들어온 것은 판단할 때 알 수 없다).
- **남는 오탐:** 퇴근 시간대에 회사를 나가 **다른 곳으로** 가는 날(저녁 약속)은 못 가린다.
  집 방향으로 움직이는지 보면 줄일 수 있지만 구현하지 않았다.
- "지금 퇴근" 은 **지금이 몇 시인지** 알아야 시각이 된다. 모르면 지어내지 않는다. "40분
  걸려" 를 쓸 수 있는 시간(예산)으로 읽지 않는다(전에는 첫 "N분" 을 예산으로 읽었다).
- 이동 시간만 알고 퇴근을 모르면 선제 주문을 하지 않는다(`situation_read` 가 퇴근 시각이
  있을 때만 이동 시간을 쓴다).
- 이동 시간·위치 동의·퇴근 시간대는 가구 선호(`profile`)로 한 번 정해 둔다.

두부가 없고 예산 25분인 가구(`check_thinq` n4, 주문 방식 auto):

| 이동 | 퇴근 모름 | 그날 말 | 위치 |
|---|---|---|---|
| 40분 | 메뉴 못 정함 | 성립 9.5분 | 성립 9.5분 |
| 30분 | 메뉴 못 정함 | 성립 9.5분 | **실패** — 확인 5분 뒤 25분 < 배송 27분 |

세부 점검에서 고친 것(9/30, `check_thinq` 11절):

- **자정.** 장면을 시각 문자열로 정렬해 "00:30 귀가 → 23:50 퇴근" 순으로 나왔다(귀가 6시간
  전부터 한 줄로 정렬). 세척 소음은 00:55 시작을 "23:00 전에 끝난다" 로 판단했다(조용 시간을
  23:00~06:00 **구간**으로 보고 겹치는 분을 센다 — 06:00 은 층간소음 규칙의 야간 경계). 위치의 퇴근 시간대가 자정을
  걸치면(21:00~02:00) 00:30 퇴근을 못 찾았다. "새벽 1시"·"밤 12시 반"·"아침 8시" 를 13:00·
  12:30·20:00 으로 읽었다.
- **알레르기.** 조달 스킬의 기피 필터가 이름 정확 일치라, 기피어 '새우' 인 가구에 '새우젓'·
  '꽃게' 를 자동 주문했다(메뉴가 먼저 걸러 파이프라인에서는 닿지 않았다 — 스킬 단독으로 뚫려
  있었다). 이제 메뉴와 같은 포함 일치다. 시연의 "확인 요청에 동의했다고 가정" 도 **못 먹는
  재료로 멈춘 것은 가정하지 않는다.**
- **말한 귀가 시각을 믿는다.** 위치 추정이 말한 귀가를 덮었고, 퇴근+이동과 말한 귀가가 서로
  맞지 않아도 조용히 넘어갔다. 이제 말한 귀가를 따르고 어긋남을 근거에 남긴다.

위치는 **입력이 없다는 것**이 장점이고, 대가는 확인 시간과 남는 오탐이다.

### 남은 약점을 어떻게 다뤘나 (9/30)

코드로 "맞출" 수 없는 것이 있다. 할 수 있는 것은 근거 있는 값으로 바꾸거나, 범위 양 끝에서
재거나, 가구가 정하게 열고 값에 따라 무엇이 바뀌는지 재는 것이다(`python assumption_sensitivity.py`).

| 약점 | 처리 | 결과 |
|---|---|---|
| 애매한 시각 ("1시 도착") | 지금 시각이 있으면 **가까운 앞쪽**, 퇴근·귀가가 둘 다 있으면 **앞뒤가 맞는 조합**(귀가가 퇴근 뒤 3시간 안), 그래도 모르면 저녁으로 읽고 **애매했다고 근거에 남긴다** | 지금 00:20 이면 "12시 반 퇴근, 1시 10분 도착" → 00:30·01:10. 지금 시각이 없으면 12:30·13:10 과 함께 "애매했다" |
| 위치 오탐 (다른 곳으로 가는 날) | 확인 시간 동안 **집까지 거리가 0.3km 이상 줄었는지**(가정) 본다 | 거리가 안 줄면 퇴근이 아니다. 휴대폰이 거리를 안 보내면 방향은 못 보고 그렇다고 남긴다. **집 쪽으로 가다 다른 데 들르는 날은 여전히 못 가린다** |
| 조용 시간 끝 07:00 | **06:00** — 「공동주택 층간소음의 범위와 기준에 관한 규칙」의 야간(22~06시) 경계. 말하지 않은 조용 시각 기본값도 23:00 → **22:00** | 참고 기준이다 — 세척기 소음이 그 규칙의 대상이라는 뜻은 아니다 |
| 식사 20분 | **30분** — 통계청 2019 생활시간조사의 한 끼 25(평일 아침)~39분(토요일 저녁) 범위 안. 평일 저녁 값 자체는 확인 못 함. 가구가 `eat_min` 으로 바꾼다 | 25·30·39분 **모두에서 네 가구의 소음 판단·세척 코스가 같다** — 결론이 이 값에 기대지 않는다 |
| 직접 장보기 +15분 | 근거 없음 — 가구가 `shop_detour_min` 으로 정한다 | 퇴근길 1인은 **15분까지 성립(24.5/25), 20분부터 미달성**. 나머지 세 가구는 10~25분 모두 성립 |
| 위치 확인 5분 | 근거 없음 — 가구가 `location_dwell_min` 으로 정한다 | 두부 없는 25분 가구에서 이동 30분이면 **확인 3분까지 성립, 5분부터 실패**. 이동 37·40분은 0~10분 모두 성립 |

결론이 가정에 기대는 곳은 "퇴근길 1인이 직접 장보기로도 되는가" 와 "이동이 짧을 때 위치로
되는가" 두 곳이고, 그 경계값을 위 표에 적었다. 식사 시간은 결론에 영향이 없었다. 이동이 짧은
가구에서는 그 5분이 성패를 가른다. 확인 5분·퇴근 시간대는 **가정**이다.

### 냉장고 안을 보지 못한다 — 믿는 재고가 틀리면 (9/30)

에이전트는 냉장고 안을 **보지 못한다.** 재고는 가구 정보·사람의 말·가정(양을 모르면 300g)
에서 오고, 확실히 아는 것은 **자기가 주문한 것**과 **저울로 잰 사용량**뿐이다. 그런데
시뮬레이터는 "믿는 재고 = 실제" 였다 — 틀린 경우를 한 번도 돌려 보지 않았다.

`belief_gap.py` 는 믿는 목록을 그대로 두고 **저울에 올리는 순간에만** 실제가 드러나게 한다.
가구마다 메뉴의 주재료에 틀림 넷을 넣었다.

재고를 **어디서 알았나**(`source`)에 따라 두 판을 쟀다. 메인 네 가구는 **장부** — 이 서비스로
장을 봐 와서 주문 기록으로 양·넣은 날을 안다(가정, 9/30 결정). **말로 받은 재고**는 확신이
낮아 보관 확인 단계에서 **한 번 묻는다**(퇴근 시각을 알면 퇴근길, 모르면 집에서 · 개입 +1).

| 가구 (주재료) · 재고 출처 | E1 있다고 믿는데 없음 | E2 없다고 믿는데 있음 | E3 양이 모자람(30%) | E4 보관일 틀림(기한+2일) |
|---|---|---|---|---|
| 야근 1인 (배추) · 장부 | 저녁 실패 | 메뉴 못 정함 | 저녁 실패 | 해당 없음 |
| 맞벌이 2인 (배추) · 장부 | 예산 초과 | 불필요 주문 | 예산 초과 | 해당 없음 |
| 알레르기 4인 (닭고기) · 장부 | 집에서 다시 짜 52.1분 | 있는 재료 두고 딴 것 삼 | 집에서 다시 짜 52.1분 | 해당 없음 |
| 퇴근길 1인 (배추) · 장부 | 저녁 실패 | 불필요 주문 | 저녁 실패 | 해당 없음 |
| 야근 1인 (배추) · 말로 받은 재고 | 메뉴 못 정함 | 메뉴 못 정함 | 메뉴 못 정함 | 메뉴 못 정함 |
| 맞벌이 2인 (배추) · 말로 받은 재고 | 미리 알고 성립 11.7분 | 불필요 주문 | 미리 알고 성립 11.8분 | 미리 알고 성립 11.7분 |
| 알레르기 4인 (닭고기) · 말로 받은 재고 | 미리 알고 성립 16.1분 | 있는 재료 두고 딴 것 삼 | 미리 알고 성립 32.2분 | 미리 알고 성립 16.1분 |
| 퇴근길 1인 (배추) · 말로 받은 재고 | 미리 알고 성립 9.5분 | 불필요 주문 | 미리 알고 성립 9.5분 | 미리 알고 성립 9.5분 |

읽는 법:
- **확인 한 번이 E1·E3·E4 를 집 밖으로 끌어낸다.** 퇴근길에 "배추 있어요? 언제 넣었어요?" 에
  답하면 없음·모자람·기한 지남을 **나서기 전에** 알고 선제 주문으로 메운다(맞벌이·알레르기·퇴근길
  모두 성립). 대가는 개입 +1. 야근 1인은 퇴근을 몰라 집에서 묻고, 살 시간이 없어 메뉴를 못 정한다 —
  틀린 걸로 조리를 시작하지는 않는다.
- **장부의 약점은 E1·E3** — 장부 밖에서 누가 먹거나 버리면(냄비 밖의 소비) 모른다. 묻지 않으니
  계량 때 안다. 대신 **E4 는 없다**(넣은 날을 기록한다).
- **E2 는 어느 쪽도 못 잡는다.** 믿음에 없는 것은 물을 대상이 아니다. 불필요하게 사거나, 있는
  재료(내일이면 버릴 닭고기)를 두고 다른 것을 산다.
- 2주 넘게 가는 장류·양념은 날짜가 틀려도 위험이 작아 묻지 않는다(가정 — 된장이 실제로 없으면
  계량 때 안다).

**말로 받은 재고를 읽는 데서 생기던 E1(10/1 고침).** 규칙 파서가 이름이 나오기만 하면 있다고
읽어 "두부 없어 배추만 있어" 에서 두부가, "새우는 없어" 에서 새우가 재고가 됐고, "닭고기랑" 에서
'고기' 를 또 읽었다. 이제 재료마다 바로 뒤의 말(없·다 썼·떨어졌·버렸)을 보고, '랑' 으로 이어진
재료는 같은 부정을 받으며, 더 긴 이름 안의 짧은 이름은 따로 읽지 않는다. 진짜 LLM 은 처음부터
맞게 읽었다. 그리고 확인 질문에서 **넣은 날을 사람도 모르면 지어내지 않고** "넣은 날 모름 —
손질할 때 냄새·색을 보라" 고 남긴다. 집에서 확인을 묻는 날은 "냉장고를 열어 확인하는 일" 을
덜었다고 세지 않는다(바로 그 일을 시키면서 덜었다고 셌다).

**이 측정이 드러낸 파이프라인 버그(9/30 고침).** 메뉴를 고를 때는 기한 지난 재료를 뺐는데,
고른 메뉴의 **부족분을 다시 셀 때는 넣었다** — 상한 배추가 "있음" 이 되어 새로 사지 않고 계량 때
그대로 썼다. 믿음과 실제가 같아도 냉장고에 기한 지난 재료가 있으면 타는 경로였다. 부족분 계산과
계량 양쪽에서 막고, 같은 것을 새로 사면 **기한 지난 것은 버리고 바꾼다**(전엔 새 배추가 옛 날짜를
물려받았다).

**측정하다 찾은 것 두 가지.** (1) 처음엔 측정 코드가 "실제로 없음" 을 한 번만 적용해,
재계획으로 세계가 초기화되자 없던 배추 99g 이 다시 생겨 E1 이 "성립" 으로 나왔다. (2)
에이전트의 재계획은 **나서기 전에 미리 돌려 보는** 것이라, 집에서 알게 된 사실로 퇴근길부터
다시 짜면 그때는 알 수 없던 정보를 쓴다(16.1분 같은 너무 좋은 값). 그래서 실제가 다르면
**발견한 시각에, 집에서, 이미 쓴 시간을 빼고** 다시 짜는 것으로 쟀다. 지금 파이프라인에서는
믿음과 실제가 같아 문제가 드러나지 않지만, 재고 확인을 넣으면 재계획도 "지금 어디서 몇 시인가"
를 알아야 한다.

### 교차 오염과 성분표 — 이름에 안 보이는 알레르기 (10/1)

**냄비 기록.** 알레르기 가구가 말한 불편 "조리 기구가 섞이지 않게 신경 쓰는 일" 은 지금까지
유일하게 못 덮던 수고였다(LLM 도 "덜어 줄 기능이 없다" 고 밝혔다). 문구로 덮지 않고 **두 기기가
아는 것을 잇는다** — 조리기는 자기 냄비로 무엇을 끓였는지, 세척기는 그 뒤 씻었는지 안다. 조리
전에 마지막 사용에 못 먹는 재료가 있었는데 씻은 기록이 없으면 알린다(손으로 씻었으면 기록이
없으니 역시 알린다 — 모르면 묻는다).

| p3 냄비의 지난 사용(가정) | 결과 |
|---|---|
| 이틀 전 다른 가족 몫 **새우 된장국**, 세척기 표준 코스로 씻음 (메인) | "그 뒤 세척기로 씻었다 — 그대로 쓴다" · 개입 2 |
| 같은 냄비, 씻은 기록 없음 | "냄비를 씻거나 다른 냄비를 쓰라" 고 알림 · 개입 **3** |

이것으로 p3 의 수고는 **3/3**, 장면은 7/7 이 된다. 다만 **덮는 것은 냄비까지**다 — 도마·칼은
기기가 아니라 기록이 없어 사람이 챙긴다(장면 문구와 결과에 그대로 적는다). 이 부분까지 "덮었다"
로 세는 것은 후하다는 점을 밝혀 둔다.

**상품 원재료.** 가공품은 이름으로 알레르기를 알 수 없다(카레가루에 분유, 맛술에 '기타가공품').
조달 스킬이 상품의 원재료 목록을 보고, 못 먹는 재료가 있거나 **속을 알 수 없는 원재료**(혼합제제·
기타가공품 등 — 식약처 C002 응답에 실제로 나온다)가 있으면 사지 않고 묻는다. 실제 출처는 식약처
「식품(첨가물)품목제조보고(원재료)」(C002, 제품별 원재료명)다. 공개 샘플 키로는 제품명 검색이 안 돼
아직 붙이지 않았고, 시뮬레이터의 원재료는 **대표값 가정**이다. C002 에 "같은 제조시설" 표시는 없다.

| 퇴근길 1인 | 성립 3/3 · 16,500원 · 또 산 것 0 | 성립 3/3 · 35,100원 · 또 산 것 4 · **수명 끝 재료 쓴 날 1** |

재료는 있던 것으로 치지 않는다.)

- **장부가 없으면 위험이 숨는다.** 날짜를 몰라 수명 끝 재료로 조리한 날이 생기고(p1·p3·p4), 알레르기
  가구는 2일차에 닭고기가 28g 뿐인 것을 **계량 때 집에서** 알아 57.4분이 걸렸다.
- **장부 없음이 더 성립하거나 더 싸 보이는 칸은 그 이유가 위험이다.** 야근 1인 3/3 은 수명 끝 두부를
  써서고(장부는 쓰지 않고 멈춘다 — 퇴근을 몰라 살 수도 없다), 맞벌이 8,400원은 2일차에 사라진 배추를
  모른 채 3일차에 실패해서다.
- 퇴근길 1인은 장부가 있으면 참기름·두부를 한 번 사서 사흘 쓴다(장부 없음은 매일 또 산다).

**이 측정이 드러낸 결함(10/1 고침).** 기한이 지났는지의 정의가 코드 안에 둘이었다 — 보관 확인은
"보관일이 수명에 **닿으면**" 버리고, 부족분·계량·재고 교체는 "**넘어야**" 버렸다. 5일 수명 두부가
5일째에 한쪽은 버릴 것, 한쪽은 쓸 것이었다. 안전 쪽(닿으면 쓰지 않는다)으로 하나로 맞췄다.

### 국물은 남아야 하고, 탈 것이 있어야 눌어붙는다 (9/29)

요리로서 결과를 다시 읽다가 셋이 나왔다.

| 무엇 | 전 | 지금 |
|---|---|---|
| **국물** | 공개 레시피에는 물이 없다(된장국 1인분 재료 합 75g). 흡수분과 졸일 만큼만 부어 **4인분 삼계탕이 국물 80g · 눌어붙음 0.90** 으로 끝났다 | 끝났을 때 남길 국물을 **식품 등의 표시기준 [별표 3] 1회 섭취참고량**(국·탕 250g, 찌개 200g, 죽 250g, 스프 150g)에서 정한다. 1인분 국물 = 참고량 − 건더기, 건더기가 더 많은 탕은 참고량의 절반(**가정**) |

### 익힘과 졸임은 다른 조건이다

제안서는 "익힘·졸임의 판단이 어려운" 사용자를 대상으로 적었는데 코드에는
졸임만 있었다. 질량비가 목표에 닿아도 닭고기가 안 익었으면 끝이 아니다.

`converge` 는 완료 조건을 둘 이상 가질 수 있다. 졸임이 먼저 끝나면
**화력을 유지하며 익을 때까지 기다리고**, 그 사이 더 졸면 물로 되돌린다.
유지 화력을 1 로 두었더니 53도로 식어 익지 않았다 — 3 이어야 한다.

## 검사가 깨지면 무엇을 하는가

검사를 만들어 두는 것과 **깨졌을 때 옳게 대처하는 것**은 다른 문제다.
가장 쉬운 길은 늘 기대값을 고쳐 통과시키는 것이고, 그러면 검사는
통과하지만 아무것도 지키지 않는다.

하루 동안 실패 네 건에 서로 다른 대처를 했다. 그 기록을 남겨 둔다.

| 실패한 것 | 원인 | 한 일 |
|---|---|---|
| `check_physics` 질량 수지 41건 | **검사 식이 틀림** (skim 이 분모도 줄이는 것을 몰랐다) | 검사를 고침 |
| `check_cooking` 익힘·표류 | **시험 설계가 틀림** (포화 상태에서 잼 / 방어를 우회함) | 시험을 다시 짬 |
| `check_consistency` 문서 수치 | 코드를 고쳐 값이 바뀜 | 문서를 갱신 |
| `check_sensitivity` STIR_RELIEF | 가정값이 실제로 결과를 지배 | **기준을 완화**하고 한계로 등록 |

**넷 중 둘은 코드가 아니라 내 검사가 틀린 것이었다.** 그래서 순서를 정한다.

```
1. 내 검사·시험이 틀렸는가      ← 가장 먼저 (실제로 하루에 세 번)
2. 산출물이 낡았는가            ← run_design.py 부터 다시
3. 코드가 틀렸는가              ← 고친다
4. 기준이 낡았는가              ← 그 기준을 정한 설정이 바뀌었는지 확인 후에만
5. 한계로 등록                  ← 위 넷이 아닐 때만, 무엇이 뒤집히는지 수치로 적는다
```

`check_all.py` 가 실패한 검사마다 이 순서를 출력한다. 기준을 바꿨으면
**왜 바꿔도 되는지 주석에 남긴다 — 남길 수 없으면 아직 원인을 모르는 것이다.**

## 어느 상수가 결과를 지배하는가 — 민감도

상수마다 출처를 적어 두었다(측정에서 역산 / 실제 조리 관찰 / 시뮬레이터
가정). **결과를 지배하는 것이 가정값이면 그 수치를 근거로 쓸 수 없다.**
그래서 상수를 20% 씩 흔들어 출하 지표가 얼마나 움직이는지 잰다
(`check_sensitivity.py`). 각 상수는 **그것이 실제로 쓰이는 시나리오**에서만
잰다 — 뚜껑을 안 덮는 판에서 뚜껑 상수를 흔들면 당연히 0 이 나온다.

| 상수 | 출처 | 출하 지표를 움직인 폭 (허용 폭 대비) |
|---|---|---|
| `STIR_RELIEF` | **가정** | **66.2%** (눌어붙음 0.5404 → 0.6066) |
| `WATT_PER_POWER` | 역산 | 48.5% |
| `LATENT_J_PER_G` | 역산 | 48.0% |
| `ABSORB_RATE` | 가정 | 10.4% |
| `LOSS_W_PER_K` | 역산 | 9.3% |
| 나머지 가정값 | 가정 | 2.8% 이하 |

### 자연어로 받는다 — LLM 을 어디에 두고 어디에 두지 않는가

LG 가 IFA 2026 에서 공개한 **씽큐 클로**는 카톡·텔레그램으로 대화하고,
루틴에 맞춰 가전 동작을 먼저 제안하며, **실행은 사람이 승인**한다.
하는 일을 뜯어보면 `자연어 → 제안 → 승인 → 실행` 이다.

우리 파이프라인은 `상황 → 계획 → 실행 → 지표` 다. 가운데는 이미 있고
**양 끝이 비어 있었다.** `thinq.py` 가 그 두 끝이다.

```
[LLM 제안]  자연어 → 상황 dict                 → 형식·범위 검사, 안전 항목은 사람 승인
[LLM 제안]  수고 → 시나리오 장면 (llm_design)   → 없는 기능·수치 약속을 버림, 실행으로 판정
[결정적]    계획 → converge → aftercare         ← 손대지 않는다
[LLM]       지표 → 사람이 읽는 문장             → 지어낸 수를 표시
```

원칙은 **"LLM 이 제안하고, 되돌릴 수 없는 결정은 검증된 계산이나
사람이 확정한다"** 다.

처음에는 "판단은 측정이 하고 LLM 은 말만 한다" 로 적었는데 너무 넓었다.
**제어**(화력·불 끄는 시점)에 LLM 을 넣지 않는 것은 맞다 — 관측 주기가
0.25~1분인데 호출이 30~60초 걸리고, 졸아 버린 국물은 되돌릴 수 없고,
200회 반복 측정과 회귀 검사가 "같은 입력이면 같은 출력" 위에 서 있다.
하지만 **사람 말을 이해하는 판단**(이 불편을 어느 기능이 덜어 주는가)은
규칙이 약하고 LLM 이 강하다. 그것까지 막을 이유는 없었다.

### LLM 이 시나리오 장면을 제안한다 (llm_design.py)

장면 틀(kitchen_beats)은 수고를 "덮었는지" 를 **문자열 포함**으로 센다.
그래서 사람이 자기 말로 한 불편은 하나도 못 덮었다.

| 입력 | 틀 | LLM 제안 (진짜 호출) |
|---|---|---|
| "냄비 앞에서 기다리는 것", "퇴근하고 뭐 해먹을지 고민하는 것" | **0/2** | 2/2 |
| p3(알레르기) 페르소나 (9/28) | 장면 5/5 인데 **수고 1/4** | 수고 3/4 · 장면 6/6 |
| p3(알레르기) 페르소나 (9/30, 중복 합친 뒤) | 수고 2/3 | 수고 2/3 · 장면 6/6 |
| p3(알레르기) 페르소나 (10/1, 냄비 기록 기능 뒤) | 수고 3/3 | 수고 3/3 · 장면 7/7 |

p3 의 "재료마다 알레르기 여부를 확인하는 일" 은 menu 의 기피 필터가
실제로 덜어 주는데, 글자가 틀과 달라 세지 않았다. 남은 하나("조리 기구가
섞이지 않게 신경 쓰는 일") 는 LLM 이 **덜어 줄 기능이 없다고 스스로
밝혔다** — 재료만 거르고 도마·칼은 보지 않는다는 이유였고, 맞다.

> **9/30 정정.** "1/4 → 3/4" 에는 **같은 불편을 두 번 센 몫**이 들어 있었다.
> 고객이 한 "재료마다 알레르기 여부를 확인하는 일" 과, 상황 추론이 덧붙인
> "재료마다 못 먹는 것이 섞였는지 확인하는 일" 은 같은 일이다. 이제
> situation_read 는 고객이 이미 자기 말로 한 불편을 추론으로 다시 더하지
> 않고 한 번만 센다(단서: "알레르기"·"못 먹" — 여전히 글자다). 합치고 나니
> p3 에서는 틀과 LLM 이 **둘 다 2/3** 이다. LLM 의 차이가 분명히 남는 것은
> 틀의 단서에 없는 **자유 문장**(위 0/2 → 2/2)이다.

LLM 이 정하는 것과 코드가 정하는 것:

| | 누가 |
|---|---|
| 불편마다 어느 기능이 덜어 주는가, 장면 문장 | LLM |
| 고를 수 있는 기능 목록 | **flow_design 을 실제로 돌려** 이번 계획에 든 것만 |
| 장면이 일어났는지 볼 지표 이름 | 도메인(KITCHEN_CAPS) |
| 없는 기능을 약속한 장면 ("로봇팔이 썬다", p1 의 "주문한다") | 버림 |
| 실행 전에 수치를 약속한 장면 ("12분 만에") | 버림 |
| LLM 이 빠뜨린 수고 중 틀이 덮는 것 (알레르기 장면) | 틀 장면으로 채움 |
| 선제 주문이 아닌데 귀가 전에 놓은 장면 | 귀가 시각으로 옮기고 기록 |
| 장면이 실제로 일어났는가 | experience_verify 가 실행해서 |

마지막 줄이 실제로 걸렀다. 자유 문장에서 LLM 이 "뭐 해먹을지 고민" 을
재고 기능에 이었는데, 그 사람 냉장고에는 급한 재료가 없어 **"임박한
재료를 먼저 고른다" 는 장면이 미달성으로 판정됐다.** 제안이 실행으로
걸러지는 구조가 동작한 사례다.

LLM 답은 매번 다를 수 있으므로 **받은 원문을 남긴다.** p3 에 준 원문을
`fixtures/` 에 저장해 두고 `check_thinq` 가 키 없이 재생한다 — 두 번
돌려도 같은 시나리오가 나온다.

### 알레르기 — 읽는 쪽이 옳아도 받는 쪽이 모르면 샌다

LLM 이 "갑각류를 못 드셔" 에서 `갑각류` 를 정확히 읽었는데, 레시피 판정이
문자열 일치라 **공개 자료 100건 중 갑각류가 든 15건이 하나도 안 걸렀다.**
규칙 파서는 "못 드셔" 를 아예 못 읽었다. 검사는 "새우 알레르기" 같은
구체어만 넣어서 통과하고 있었다.

* 범주어를 구체 재료로 푼다 (`recipe_parse.CATEGORY`) → 15건 → **0건**.
  풀자 "얇게 썬" 의 `얇게` 가 게로 걸려 부사들을 뺐다.
* 알레르기를 읽으면 **승인 없이는 실행하지 않는다**(기본값이 멈춤).
  전에는 "확인 필요" 를 적기만 하고 그대로 실행했다.
* 표에 없는 범주어(`곡류`)는 승인이 있어도 멈춘다 — 아무것도 안
  걸러지는데 사용자는 걸러졌다고 믿기 때문이다.

검사가 그것을 지킨다 — 같은 상황을 규칙으로 읽든 LLM 으로 읽든
**제어 결과**(가전 순서·개입·가열·질량비)가 같아야 한다(`check_thinq`).

### 받은 값을 그대로 믿지 않는다

LLM 은 그럴듯한 값을 지어낸다. 읽은 값은 형식·범위를 검사하고, 틀리면
기본값으로 돌아간다.

| LLM 이 준 값 | 어떻게 되는가 |
|---|---|
| `time_budget_min: 9999` | 범위 밖 → 버림 |
| `household_size: 0` | 범위 밖 → 버림 |
| `arrive_home: "저녁쯤"` | 형식 아님 → 버림 |
| `avoid: "새우"` (문자열) | 목록이 아님 → 버림 |
| 모르는 항목 | 버림 |

설명에서도 마찬가지다. 답에 있는 수를 실행 결과와 대조해, **결과에 없는
수가 섞이면 표시한다** — "12분 걸립니다" 를 지어내면 사용자가 그것을
믿기 때문이다.

그리고 알레르기처럼 **틀리면 위험한 항목**은 읽었다는 사실만 남기고
사람에게 확인을 요청한다. 씽큐 클로의 "실행은 사람이 승인" 과 같은 자리다.

### 키가 없어도 검증된다

`ask` 는 `(프롬프트) -> 문자열` 함수이고 **주입받는다.** 스킬이 관측·조작
함수를 주입받는 것과 같은 구조다.

```
API 키 있음   → anthropic SDK 로 부른다
API 키 없음   → **설치된 claude CLI 로 부른다**   ← 이 환경이 여기다
둘 다 없음    → 규칙으로 읽는다
검사          → 가짜 LLM 을 넣어 결정적으로 시험 (22/22)
              → `--live` 를 주면 진짜로 부른다 (25/25)
```

처음에는 "API 키가 없어 이 경로는 검증 못 한다" 고 적었다. **틀렸다.**
환경을 실제로 보니 키는 없어도 `claude` CLI 가 깔려 있었다. 없다고
적기 전에 찾아봤어야 했다(2026-09-15 에 같은 실수를 기록해 두었다).

진짜로 불러 확인한 것:

| | 규칙으로 읽음 | LLM 으로 읽음 |
|---|---|---|
| 읽은 상황 | 19:00 · 45분 | 19:00 · 45분 |
| 가전 순서 | inventory→…→converge | **같음** |
| 개입 / 가열 / 질량비 | 0회 · 5.5분 · 0.78 | **0회 · 5.5분 · 0.78** |
| 설명의 지어낸 수 | — | **0개** |

CLI 를 부를 때 두 가지를 조심해야 했고, 둘 다 처음에 놓쳐서 엉뚱한
답이 왔다.

* 프롬프트를 **stdin 으로** 넘긴다. 명령줄 인자로 주면 Windows shell
  인용 규칙 때문에 개행에서 잘린다 — "'아래는' 에서 끊겨 들어왔습니다"
  라는 답이 돌아왔다.
* **빈 디렉토리에서 시스템 프롬프트를 덮어써서** 부른다. 그냥 부르면
  CLI 가 사용자의 `CLAUDE.md` 를 읽고 그 규칙대로 조언한다 — 실제로
  "CLAUDE.md 규칙대로 #local 채널에 알림을 보내려 했지만" 같은 문장과
  이번 실행에 없는 숫자(25·27·48)가 섞여 왔다. **그 숫자는 우리
  검증기가 잡아냈다.**

## 실측이 없는 상수를 다루는 법 — 교반 상수

`STIR_RELIEF`(저으면 눌어붙음이 이 비율로 준다)는 **실측이 없는 가정값**인데
결과를 가장 크게 움직였다. 0.55 를 0.66 으로 올리면 눌어붙음이 0.5404 에서
0.6066 이 되어 **세척 코스가 표준에서 강력으로 뒤집혔다 — 물 11.0L 에서
16.0L 로.**

먼저 실측을 찾았다. 열교환기 fouling 문헌은 유속이 높을수록 부착이 준다는
것을 말하지만 정량값이 가정 조리 조건과 맞지 않았고, 구체적 수치가 나온
곳은 출처가 분명하지 않은 블로그였다. **그런 값을 근거로 삼으면 "가정"
이라고 정직하게 적힌 것을 "문헌 근거" 로 포장하는 셈이라 지금보다 나쁘다.**

그래서 값을 지어내는 대신 **모른다는 사실을 값에 실었다.**

```
교반이 덜어낸 몫  × STIR_RELIEF_UNCERTAINTY(±20%)  →  soil_sigma 에 합성
aftercare 는 그 분포로 코스별 기대 비용을 최소화해 고른다
```

| `STIR_RELIEF` | 눌어붙음 | 불확실폭 | 코스 | 물 |
|---|---|---|---|---|
| 0.44 | 0.4631 | ±0.1585 | 표준 | 11.0L |
| 0.55 (현재) | 0.5404 | ±0.1275 | 표준 | 11.0L |
| 0.66 | 0.6066 | ±0.0966 | 표준 | 11.0L |

상수를 ±20% 흔들어도 **출하물(코스·물)이 바뀌지 않는다.** 민감도 검사에서
이 항목은 66.2% 에서 **0.00%** 가 됐다.

남은 사실은 숨기지 않는다. **눌어붙음 점수 자체는 여전히 상수에 흔들린다**
(0.4631~0.6066). 점수를 그대로 인용할 때는 이 폭을 함께 말해야 한다.
안정된 것은 그 점수로 내리는 **결정**이다.

## 무엇이 진짜이고 무엇이 대체인가

| 구성 | 상태 |
|---|---|
| 설계 루프 · 플래너 · 스킬 레지스트리 | **진짜** — 키 없이 동작 |
| 계획 계산 (전제조건 역추적 + 위상 정렬) | **진짜** — `planner.py` |
| 시나리오–실행 대조 검증 | **진짜** — 장면마다 `verified_by` 스킬 로그 확인 |
| 기기 API 규격 | **진짜** — ThinQ Connect 로 교체 가능한 형태 |
| 자료 수집 (`recipe_source`) | **진짜** — 식약처 공개 API 실호출, 100건 캐시 |
| 기기 내부 동작 | **시뮬레이터** — 증발·건조는 단순 1차 모델, 실측 아님 |
| 열 모델 | **열량 수지** — 투입·방열·잠열로 계산. 상수는 두 가지 실제 값에서 역산한 가정 |
| 흡수·거품·익힘 계수 | **가정** — 일반적인 조리 자료 범위에서 잡았고 실측이 아니다 |
| 끓는점 상승 | **없음** — 염도 자료가 없어 넣지 않았다 (졸수록 농도가 올라 실제로는 오른다) |
| 냄비 안 온도 분포 | **없음** — 온도가 하나뿐이라 "젓지 않으면 바닥이 탄다" 를 온도로 표현하지 못한다 |
| 고기가 익으며 내는 물 | **없음** — 채소 방출은 시작 시 더하는데 고기는 조리 중에 나온다 |
| 공개 레시피 100건 | **실제 공공 자료** (식약처 COOKRCP01) |
| 개인 조리 기록 3건 | **합성 데이터** — 실측 교체 필요 |
| 공개 레시피의 목표 질량비 | **가정** — 조리법별 기본값, 첫 조리 실측으로 대체되는 구조 |
| 눌어붙음(오염도) | **조리 중 실측** — 시뮬레이터 모델이며 실측 센서값은 아님 |
| LLM 기반 계획 (`agent.py`) | **미검증** — 현재 제출 경로가 아니다 |
| 자연어 읽기·장면 제안 (`thinq.py`·`llm_design.py`) | **진짜 LLM 으로 확인** — claude CLI 호출, 원문은 `fixtures/` 에 남겨 키 없이 재생 |
| 장보기 상점 (`store.py`) | **시뮬레이터** — 공개 레시피 재료에서 고른 236품목, **분류별 합성 가격**. 주류는 주세법상 온라인 판매 금지라 넣지 않았다. 즉시배송이 안 파는 것(한약재·특산품)은 **가정**이며 결과가 이것에 민감하다(찹쌀). 즉시배송 27분은 B마트 평균(보도 기준, 시점·지역에 따라 다를 수 있다). 상한 1시간이면 네 가구 중 셋이 성립하지 않는다(`delivery_sensitivity.py`). 직접 장보기에 드는 시간(퇴근길 +15분, 집에서 +25분)은 **가정**이다(`mode_sensitivity.py`) |

## 비용과 키

제출 경로(`run_design.py`)는 **표준 라이브러리만** 쓴다. `pip install` 대상 0개, 유료 API 0개.

| 항목 | 키 | 비용 |
|---|---|---|
| 실행 전체 | 불필요 | 0원 |
| 식약처 레시피 DB | 공개 `sample` 키로 동작 / 발급키는 무료 | 0원 |
| ThinQ Connect | 교체 경로로만 문서화, 현재 미사용 | — |
| Claude API | `agent.py` 전용, 제출 경로 아님 | (유료, 미사용) |
